# 适用性与目标形态

## 不先假定答案

领域包是一种产品化和组合边界，不是所有项目的默认终点。先确认复用者、领域状态、独立演进诉求和运行方式，再选择最小充分形态。

## 形态选择

| 主要特征 | 默认形态 | 何时升级 |
| --- | --- | --- |
| 无状态算法、纯函数或通用类型 | 库 / SDK | 需要独立运行、权限、版本或多语言访问 |
| 单产品内部模块，只被同一进程使用 | 内部模块 | 出现独立团队、生命周期或跨进程消费者 |
| 有稳定服务边界，但只有确定性系统调用 | API 服务 | 需要 Agent 判断、安装式扩展或多种人机入口 |
| 只向某一宿主贡献界面或命令 | 插件 | 需要脱离宿主独立完成领域流程 |
| 有权威领域事实、多类消费者和独立生命周期 | 领域能力包 | 已是目标形态，继续完善契约与发行 |

领域包可以内部保持模块化单体，也可以由多个服务组成。微服务数量不是成熟度指标；边界清晰、契约一致、可独立验证和可交付才是。

## 准入问题

至少回答以下问题：

1. 能否用一句话说明该领域包独占的业务责任？
2. 哪些资源、规则和判定只有它有权修改或解释？
3. 谁会消费能力，为什么普通库或单一 API 不够？
4. 是否需要独立版本、权限、部署、数据或升级周期？
5. 脱离通用宿主后，是否仍能完成一个有价值的单领域用例？
6. 宿主替换后，能力是否仍能通过稳定契约复用？

前三项无法明确时，先做领域分析，不开始工具、页面或发行改造。

## 最小可行领域包

最小形态必须包含：

- 清晰的限界上下文与唯一事实来源；
- 稳定资源标识及版本化能力契约；
- 至少一个真实消费者使用的执行入口；
- 明确的权限、错误、并发或幂等语义；
- 可识别版本、依赖和运行要求；
- 能证明独立业务价值及跨渠道一致性的测试。

以下内容均为按需贡献，不得为了清单完整而空建：Skill、CLI、MCP、SDK、完整 Web、嵌入视图、事件、算法库、本地运行时和共享服务。

## 停止条件

出现以下情况应暂停实施并请求产品决策：

- 权威数据所有者存在争议；
- 单任务与跨任务流程无法区分；
- 同一资源需要多个系统同时写主数据；
- 目标消费者、权限或部署边界尚未确定；
- 为兼容旧系统需要改变业务语义或不可逆迁移数据。
