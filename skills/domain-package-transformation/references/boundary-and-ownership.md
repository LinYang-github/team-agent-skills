# 边界与所有权

## 先按业务事实划分，不按技术组件划分

领域边界首先回答“谁有权创建、修改、发布和解释这项业务事实”，然后才决定 API、MCP 或事件。每种资源必须有唯一事实来源；其他系统保存稳定引用或不可变快照，不复制一套可写主数据。

## 默认责任模型

| 责任 | 领域能力包 | 通用宿主/编排层 | 外部领域系统 |
| --- | --- | --- | --- |
| 本限界上下文内的领域资源和内部聚合 | 拥有 | 保存引用和摘要 | 保存引用或快照 |
| 单领域工作流、状态机与就绪规则 | 拥有 | 展示结果 | 不重新计算 |
| 领域算法及业务判定 | 拥有 | 发起调用 | 使用公开结果 |
| 领域修订、发布和审计事实 | 拥有 | 记录关联 | 消费已发布版本 |
| 通用工作项、会话和 Agent 执行 | 不拥有 | 拥有 | 不拥有 |
| 一项工作关联几个领域资源 | 不决定 | 拥有 | 不越权修改 |
| 跨领域资源关系与总体进度 | 不拥有 | 拥有 | 提供自身状态 |
| 各领域数据库 | 独立拥有 | 独立拥有宿主数据 | 独立拥有自身数据 |

领域包可接收宿主传入的 `ContextEnvelope`、主资源引用和相关资源引用，但不得自行扫描宿主项目列表或推断跨领域基数。

## 关系表达

跨领域关系至少包含资源类型和稳定 ID、来源领域或服务标识、被引用修订或快照版本、关系类型，以及必要的时间、状态和追溯信息。

若下游结论必须可复现，应引用上游不可变发布快照，而不是“当前最新数据”。实时查询适用于展示和协作，不替代正式基线。

## 常见反模式

- 让一个领域后端维护其他客户端或业务系统的项目列表。
- 多个系统直接读写同一 SQLite 表或共享数据库 schema。
- 宿主复制领域状态机并独立判定能否进入下一阶段。
- 领域页面自行决定一个工作项应创建或关联几个领域资源。
- 用显示名称、页面标题或数组下标代替稳定资源 ID。
- 把所有领域能力汇入一个可直接操作多库的“万能 MCP”。

## 验证问题

1. 每项可写业务事实是否只有一个权威所有者？
2. 脱离宿主后，领域包能否继续完成至少一个有价值的单领域用例？
3. 替换领域包实现时，宿主能否只依赖稳定契约完成迁移？
4. 跨领域链路能否追溯到明确版本或发布快照？
5. 是否存在绕过 API 的跨库写入或重复业务判定？
