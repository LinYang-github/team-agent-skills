# 强类型流程组合

## 控制顺序与数据连接分开建模

多节点领域流程必须区分两类关系：

- `controlDependencies` 只表达进入顺序、导航和人工确认约束，不传递数据，也不因上游内容变化自动判定下游事实失效。
- `dataBindings` 显式连接源节点输出端口与目标节点输入端口，负责资源、版本、基数和作用域兼容性。

禁止让调用方、页面或节点顺序推断数据连线。编译器应分别检查控制图和数据图无环，并拒绝悬空端口、未知资源、版本不兼容、基数不匹配及作用域越界。

## 端口和外部槽位

每个稳定端口至少声明端口 ID、资源类型、接受的 schema 版本、基数、作用域、必需策略和来源策略。本域输出使用 canonical 资源；外部领域输入同时声明：

1. 同名 `externalSlot`，描述允许的外部资源类型、版本和必需性；
2. `sourcePolicy: external-resource` 的输入端口；
3. 运行时 `ResolvedInputRef`，至少包含稳定资源 ID、修订、schema 版本和内容哈希。

领域包只能校验自己保存或宿主提交的版本化引用，不得把外部系统伪装成本领域流程节点，也不得直接访问外部数据库。未形成稳定契约的外部输入应保持可选并报告 warning，不生成虚假引用；必需外部输入缺失时 readiness 必须阻断。

## 适配器必须受控

只有直接端口不兼容时才使用适配器。适配器必须由服务端注册并声明稳定 ID、版本、源类型、目标类型、接受版本和是否有损。流程草案只能引用已注册适配器，不能携带脚本、表达式或任意字段映射。有损适配产生显式 warning，并在应用或发布前要求确认。

## 编译、预览和应用共享证据

规范化节点、控制依赖、数据绑定、端口版本和适配器版本应进入确定性 `planHash`。候选计算、compile、preview、apply 和 readiness 必须复用同一个服务端端口解析器：

- preview 固化当前任务版本、流程修订、计划哈希和全部已解析输入引用；
- apply 重新校验这些证据，任何版本、修订、绑定或输入哈希变化都使旧预览失效；
- 发布快照保存最终计划、绑定、适配器和实际消费的 `ResolvedInputRef`，用于回答一次发布究竟依赖了哪些上游事实。

输出端口可以声明由 JSON Pointer 等稳定机制表达的语义投影。失效传播只沿发生语义变化的数据绑定标记直接消费者；未声明投影时按整个输出保守判定。控制依赖不触发数据失效，下游只有在自身输入实际变化并重新确认后才继续传播。

## 验证

- 合法流程完成 catalog → compile → preview → apply → readiness → publish → snapshot 回读。
- 控制图和数据图分别覆盖环、悬空引用和重复绑定测试。
- 外部输入覆盖缺失、类型不符、版本不兼容、修订或哈希过期。
- 适配器覆盖未注册、类型不兼容和有损确认。
- 修改已解析输入后，旧 preview 必须失败；未改变语义投影时不应误伤无关下游。
- 发布快照中的计划哈希、绑定和输入引用必须与发布回执及回读内容一致。
