# 领域能力包改造

## 目标

把已有业务产品收敛为一个可独立演进的领域能力单元：领域事实只有一个权威实现，对人、Agent 和其他系统提供一致能力，并能以明确版本安装、运行、发现、升级和卸载。

“一个领域包”表示统一的领域边界、能力标识、契约和发行生命周期，不表示一个仓库、一个进程、一个安装文件或一个 Skill。不要为了领域包形式强制拆微服务，也不要要求每个产品同时提供所有交互渠道。

## 先识别请求模式

- **评估**：默认只读，检查现状和证据，给出适用性、成熟度及差距，不修改项目。
- **规划**：形成目标边界、决策、迁移阶段和验收标准；没有明确授权时不实施。
- **实施**：先保护工作树，遵守项目变更流程，按可回滚阶段实现并验证。
- **审查**：比较声明的领域包能力与源码、构建物和运行行为，报告不一致及风险，不自动修复。

用户的实施授权不自动包含提交、推送、发布、数据迁移或覆盖客户端配置。

## 适用性门禁

开始设计前先判断目标究竟需要领域包、普通库、内部模块还是单一服务接口。领域包通常适合同时具备以下特征的产品：

- 有稳定且可命名的业务边界、领域资源或业务判定；
- 有自己的事实来源、状态、不变量或发布生命周期；
- 需要被两类以上消费者复用，例如 Web、自动化脚本、Agent 或其他系统；
- 需要独立版本、权限、运行或交付边界。

若只是无状态算法复用、单进程内部代码整理或单一消费者接口，不要把领域包复杂度强加给项目。完整判断读取 [适用性与目标形态](references/qualification-and-target-shape.md)。

## 核心边界

- 领域包拥有本限界上下文内的领域事实、内部聚合、业务规则和单领域流程；通用宿主拥有工作项、会话、跨领域关系、资源基数选择、Agent 执行和总体进度。
- 每项可写业务事实只能有一个权威所有者。跨领域协作使用稳定资源 ID、版本化契约、事件或快照，禁止共享业务数据库和跨库直写。
- 应用服务是各调用渠道复用的用例入口；跨进程时 API/事件是机器契约，SDK 是客户端封装。CLI、MCP 和 Web 不得各自复制业务规则。
- Skill 负责领域判断、信息缺口和执行护栏；CLI、MCP、API 执行能力；SDK 简化程序调用。自然语言说明不能替代机器契约。
- 单任务完整页面属于领域包；多任务、跨领域编排页面属于宿主；卡片、侧边栏或 MCP App 仅在确有嵌入需求时作为可选贡献。
- 宿主持久化稳定的领域、视图和资源引用，不持久化内部 Web 路由、随机端口或深链。完整页面启动地址由当前领域实例从注册视图解析，用完即弃。宿主返回上下文必须是不透明、短期、不持久化的值，领域包不得把它解析为 URL 或开放跳转。
- 本地项目模式存在多项目误共享风险时默认隔离；团队共享服务必须显式选择，并具有与其暴露范围相称的认证、租户、权限和审计边界。

## 工作流程

1. **建立证据化现状图**：读取 `AGENTS.md`、README、领域模型、业务服务、算法、存储、接口、页面、CLI、MCP、Skill、安装器和构建发行配置；列出仓库、制品、命令、进程、静态资产和数据位置。结论标记为代码事实、运行证据、推断或待确认决策。
2. **决定是否采用领域包**：比较库、模块、服务、插件和领域包的成本，明确目标消费者及不可缺少的贡献面；不以“支持 AI”为由默认加入 MCP 或 Skill。
3. **划定所有权**：制作“领域包 / 通用宿主 / 外部领域”责任表，先确定资源和状态归属，再选择通信协议。涉及单任务、多任务或跨领域关系时读取 [边界与所有权](references/boundary-and-ownership.md)。
4. **定义公共能力**：为稳定资源和操作声明能力 ID、风险、权限、幂等性、确认策略、版本及实际需要的渠道，区分 public、compatibility 与 internal。设计清单或写入协议时读取 [能力与契约](references/capability-and-contract.md)。
5. **收敛交互与调用表面**：让 Web、CLI、MCP、SDK 等适配器复用应用服务和公共契约，按任务复杂度选择页面形态，按意图、风险和上下文决定 Skill 数量。读取 [交互表面与适配器](references/surfaces-and-adapters.md)；涉及宿主打开领域页面、长 URL、嵌套应用壳或返回上下文时读取 [注册视图与宿主交接](references/view-registration-and-handoff.md)；设计命令名称、命令树、输出或自动化契约时同时读取 [CLI 设计](references/cli-design.md)。
6. **明确运行和发行**：区分逻辑包、发行制品、命令、长驻/临时进程、静态资产及业务数据；只为真实部署形态设计本地隔离、共享服务和安装态发现。读取 [运行与发行](references/runtime-and-distribution.md)。
7. **渐进迁移并验证**：优先冻结边界和契约，再收敛共享业务实现，随后迁移适配器和页面，最后验证发行与兼容；不要一次性重写。读取 [迁移与验收](references/migration-and-validation.md)。

## 关键决策规则

### 贡献面不是必选套餐

领域包必须有领域边界、能力契约、版本和至少一个可执行入口。Skill、CLI、MCP、SDK、完整 Web、嵌入视图和事件按消费者需求选择；未选择的渠道要说明原因，不创建占位实现。

### Skill 数量按职责决定

领域判断与设施运维在意图、授权、上下文和维护责任明显不同时，通常保留两个 Skill，并共享系统事实和能力契约。只有领域很小、两类请求总是共同发生，或目标客户端只能可靠注册一个入口时，才采用一个入口并在内部按 reference 分流。

### MCP 不是服务间默认总线

MCP 适合 Agent 工具调用、资源发现和可选嵌入视图。确定性系统集成优先采用版本化 API、事件或快照；只有确实需要模型参与理解、判断或工具选择时才由 Agent 经 MCP 编排。

### MCP App 保留最后成功内容

MCP App 必须把初始 `toolresult`、兜底和用户刷新收敛到单一协调器。初始结果可在 `connect()` 前后到达；只有在有界等待窗口内仍没有结果时才发起兜底，且最多一次。用请求代次或取消机制防止旧结果覆盖新意图。已有有效内容时，后续失败只能降级为非阻断提示，用户刷新开始时也不得清空最后成功内容。至少区分 MCP 未注册或连接失效、领域 API 不可达、工具业务错误和 schema 校验失败，不用一个“服务不可用”覆盖所有故障。禁止用任意长 `sleep`、无限重试或清空页面隐藏竞态。

### 视图注册不是 URL 模板注册

宿主只向领域包提交 `viewId`、稳定资源引用、可选领域阶段和呈现模式，由领域实例的 `launchResolver` 返回完整启动地址。禁止把 `routeTemplate` 发给宿主替换参数，也禁止 CLI 或 MCP 复制领域路由。`hosted` 模式隐藏领域产品级的品牌、任务中心、全局助手、设置和账户，只保留当前资源、领域单任务流程和业务编辑区；只有宿主实际提供版本化、可调用的返回桥接时才显示来源返回，不因为存在不透明 token 或浏览器 history 就生成该操作。`standalone` 才显示完整领域应用壳。

### CLI 是稳定产品接口

领域包若提供 CLI，应有一个稳定主命令，将领域业务、运行运维、客户端集成和包检查置于清晰命名空间；脚本可依赖的输出、退出码和错误语义必须版本化。同时提供业务、运行和 Agent 集成时，默认使用 `<product>ctl`，并保留 `workspace init`、`runtime start|stop|status|doctor`、`integration install|status|uninstall` 和 `mcp serve` 这些稳定语义。程序安装、工作区初始化和客户端集成安装是三种不同动作，不得都用含义不明的根级 `install` 表示。正式写入至少支持 `expected-version` 和幂等键，`dry-run` 必须保证无副作用；JSON 成功数据只写 stdout，诊断只写 stderr。

## 输出契约

根据请求模式交付相应内容，至少说明：

1. 是否适合领域包及被否决的替代形态；
2. 当前事实、证据来源和不确定项；
3. 领域包、宿主与外部领域的所有权；
4. 能力及贡献面矩阵、进程和发行模型；
5. 目标架构、差距、分阶段任务和决策点；
6. 兼容、迁移、回滚和安全边界；
7. 自动化验证、干净安装态验证及人工业务验收；
8. 未解决风险和需要用户确认的产品语义。
