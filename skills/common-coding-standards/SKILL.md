# 通用编码规范

## 目标

为 C++、Java、C#、Python、Go、Vue/TypeScript 以及其他项目提供共同的工程底线，让代码更易读、可诊断、可测试、可维护和可交付。规范回答“应达到什么结果”和“如何做出可验证的工程决策”；具体语言技能负责回答“在该语言中如何实现”。

## 适用范围

当用户要求以下事项时启用本技能：

- 统一命名、代码可读性、注释和公共 API 文档。
- 规范异常、错误、重试、降级和失败恢复。
- 统一日志级别、结构化字段、脱敏、轮转、保留和生产输出策略。
- 处理输入校验、数据边界、配置分层、命令行覆盖、密钥和环境差异。
- 设计资源生命周期、超时、取消、并发和幂等边界。
- 建立测试、静态检查、构建、依赖审查和质量门禁。
- 规范单服务的目录、端口、升级回滚、健康检查和离线交付边界。
- 统一 Git 提交、变更记录、代码审查和交付说明。
- 治理 VibeCoding 产生的重复代码、隐式依赖、临时方案和不可定位故障。

当前规范默认适用于桌面端和服务端等工程项目；移动端、UI/UX 视觉和具体业务规则不由本技能推导。

构建、测试和生产运行默认不依赖未锁定的在线资源、CDN、远程脚本、远程字体或远程图片；优先使用仓库内资源和已锁定依赖。业务系统按契约访问的后端 API 不属于此限制。

## 与专项技能的边界

| 范围 | 本技能负责 | 专项技能负责 |
| --- | --- | --- |
| 命名和可读性 | 跨语言原则和验收标准 | 语言习惯、关键字和工具配置 |
| 异常和错误 | 分类、边界、恢复和信息安全 | 具体异常类型、错误对象和框架写法 |
| 日志 | 级别、字段、频率、脱敏、轮转和保留原则 | 具体日志库、采集器和部署配置 |
| 测试 | 分层、风险匹配和质量门禁 | JUnit、pytest、Go test、Vue Test 等 |
| 依赖 | 来源、版本、许可证和供应链风险 | npm、Maven、NuGet、pip、Go module 等 |
| 前端 | 通用代码质量和交付原则 | Vue、路由、状态、组件和浏览器工程 |
| UI/UX | 不负责界面表达 | ui-ux-standards |
| 业务规则 | 不定义领域含义 | 产品、领域和系统业务规范 |

专项技能与本技能冲突时，遵循用户明确要求、项目现有约束、专项技术约束、本技能默认建议的顺序；需要偏离时记录原因和影响。

## 不可违背的原则

1. **命名表达意图。** 名称应体现职责、状态或领域含义；避免无意义缩写、万能变量名和无法区分的重复名称。
2. **注释解释原因。** 注释优先说明约束、取舍、兼容性和风险，不重复代码字面含义；公共接口和复杂规则必须有可维护的文档。
3. **错误不可静默。** 不吞异常、不使用空 catch、不用特殊返回值掩盖失败；错误必须进入明确的处理、上报、恢复或终止路径。
4. **边界先校验。** 外部输入、配置、文件、消息和 API 响应先解析、校验和映射，再进入核心逻辑。
5. **日志可诊断且不泄密。** 采用结构化字段和合适级别，记录请求 ID、资源 ID、错误码等必要上下文；禁止输出密码、Token、Cookie、密钥和未脱敏敏感数据。
6. **副作用有所有权。** 文件、连接、锁、线程、定时器、订阅、缓存和临时数据要有创建、使用、释放、失效和异常路径。
7. **失败可恢复。** 为超时、取消、重复执行、权限失效、外部服务失败和部分成功定义可预测的恢复或降级行为。
8. **质量门禁不可绕过。** 不通过删除测试、关闭检查、静默忽略错误或降低安全要求来制造“通过”。
9. **依赖来源可追踪。** 依赖、许可证、版本和构建资源可审计；不引入无法确认来源或未锁定版本的代码和在线资源。
10. **提交保持单一意图。** 一个提交解决一个可描述的问题，避免把无关格式化、重构和功能混在一起。
11. **先测量再优化。** 性能、并发和缓存改动应有基线、目标和回归验证，不用复杂抽象掩盖实际瓶颈。
12. **例外显式记录。** 无法遵循规范时，说明原因、范围、风险、维护责任和重新评估条件，不把例外伪装成默认做法。
13. **配置分层且可覆盖。** 用户可调整的运行配置与软件内部配置分开维护，并提供稳定的命令行覆盖入口；升级不得覆盖用户配置，敏感值不得因追求统一而暴露在命令行中。
14. **单服务可独立交付。** 服务必须明确可写目录、网络入口、健康状态、升级回滚和离线运行条件，不能把开发环境中的隐含条件带入生产部署。

## 标准工作流

1. **确认范围**：明确项目、语言、模块、公开接口、运行环境和本次是审查、设计、实现还是回归。
2. **读取基线**：检查项目说明、构建配置、依赖清单、入口、错误处理、日志、测试和 Git 状态。
3. **识别边界**：区分输入/输出、业务规则、基础设施、副作用、异常路径和资源所有权。
4. **应用通用规则**：先处理命名、异常、日志、配置、安全、测试和提交边界，再应用语言或框架专项规范。
5. **最小改动**：优先修复明确风险，保持公开行为兼容；抽象必须有稳定的复用场景和清晰的依赖方向。
6. **验证质量**：运行与改动相关的格式化、静态检查、类型检查/编译、单元测试、集成测试或构建，并检查失败路径。
7. **记录交付**：说明修改、兼容性、验证命令、遗留风险、未覆盖边界和后续迁移建议。

## 输出契约

每次执行结束时至少给出：

处理模式：审查 / 设计 / 实现 / 回归

目标范围：项目、语言、模块、接口或提交

工程决策：命名、异常、日志、数据边界、资源生命周期、安全、测试和兼容策略

修改内容：文件、公开接口、配置、依赖和迁移影响

验证结果：实际执行的检查、测试、编译、构建或替代验证

遗留风险：未覆盖的异常路径、环境差异、依赖风险和后续建议

## 禁止事项

- 不把通用规范写成某一种语言或框架的实现教程。
- 不用 utils、common、helper 等宽泛目录掩盖无法归属的业务逻辑。
- 不在页面、控制器或入口中重复实现鉴权、错误解析、日志格式和配置读取。
- 不把异常、日志、配置和测试问题全部推迟到“以后统一处理”。
- 不提交密钥、个人数据、构建产物、临时文件、调试代码或未经审查的在线资源。
- 不因为格式化、重命名或机械迁移而扩大用户请求范围。
