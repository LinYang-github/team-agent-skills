# 项目文档治理

本规范统一 README 和已实现系统的项目文档，不定义需求规格或 Spec 工作流。项目已有文档约定优先；如采用不同目录或格式，应在项目贡献指南中说明。

## 职责边界

项目文档用于说明已实现系统的使用、开发、构建、部署和维护方式。

以下内容暂不由本规范定义，由独立的 Spec 框架管理：

- 需求规格和业务目标拆解
- 变更提案、设计任务和任务状态流转
- 验收标准及规格与代码的映射
- Spec 的评审、批准、归档和版本策略

架构文档可以记录当前已落地的结构和决策，但不替代未来的 Spec。API 文档若有机器可读契约，以契约文件为权威，Markdown 只说明使用方式和引用入口。

## 推荐目录

项目按实际需要逐步建立目录，不要求一次性创建全部文件：

```text
README.md
docs/
├── architecture/    # 当前架构、模块边界、已落地决策
├── development/     # 环境、构建、测试、调试
├── api/              # 接口使用说明和契约索引
├── deployment/       # 环境、配置、发布、升级、回滚
├── operations/       # 监控、排障、运行手册
└── changes/          # 版本变更记录
```

不要把临时笔记、未经确认的方案、个人环境记录或 Spec 草稿混入正式项目文档目录。

## README 规范

README 是项目入口，优先回答“这是什么、能做什么、如何启动、详细信息在哪里”：

```text
# 项目名称
## 项目简介
## 核心能力
## 项目边界
## 技术栈
## 目录结构
## 环境要求
## 快速启动
## 配置说明
## 测试与质量检查
## 部署入口
## 文档索引
## 常见问题
```

README 只保留上手所需信息。完整 API 细节、长篇故障排查、架构讨论和历史记录应放入 `docs/`，并从 README 提供链接。

快速启动必须包含：

- 支持的操作系统、运行时和工具版本
- 安装或准备依赖的步骤
- 可复制的启动命令及执行目录
- 默认访问地址或验证方式
- 常见失败原因和指向详细文档的链接

## 文档元数据

除 README 外，生命周期较长或影响交付的文档建议在顶部使用统一元数据：

```yaml
---
title: 服务部署说明
status: active
owner: backend-team
last_updated: 2026-08-26
applies_to: v1.x
---
```

字段约束：

- `title`：文档标题。
- `status`：使用 `draft`、`active`、`deprecated` 或 `archived`。
- `owner`：维护团队或责任角色，不能只依赖个人姓名。
- `last_updated`：最后一次实际核对内容的日期。
- `applies_to`：适用版本、模块或环境。

同一项目只能选择一种元数据写法；不使用 YAML 时，可统一采用 Markdown 表格。

## 写作和示例

- 中文项目默认使用中文；命令、路径、类名、接口名、配置键和错误码保留原文。
- 标题层级连续，一个章节只回答一个主要问题。
- 先给结论和操作步骤，再补充背景、原理和限制。
- 命令注明执行目录、前置条件和预期结果，确保可以复制验证。
- 复杂流程使用表格、流程图、状态转换或输入输出表，不用大段叙述掩盖关键条件。
- 示例不得包含真实密钥、Token、账号、个人数据、生产地址或未经确认的协议。
- 代码示例应与当前实现保持一致；过期示例必须修复、标记或删除。

## 生命周期与同步

以下变更必须检查并同步受影响文档：

- 公开 API、消息格式或错误契约变化
- 配置项、环境变量、依赖或运行时要求变化
- 数据库 schema、迁移、升级或回滚方式变化
- 构建、部署、启动、探活、发布或恢复流程变化
- 模块边界、目录结构或用户操作流程变化

合并请求或交付记录应标记文档影响：`无 / README / 开发 / API / 部署 / 运维 / 变更记录`。文档与代码不一致时，以可验证的当前实现为准，并优先修正文档或明确记录例外。

## 可编辑文档制品验收

当 Markdown、HTML 或结构化数据被转换为 DOCX、ODT 等可编辑文档时，源文件正确不等于交付制品正确。转换工具、模板和办公软件可能通过样式继承引入缩进、对齐、分页和字体偏差，因此必须以最终制品为验收对象。

- 生成后必须渲染最终文件并逐页检查，不得只检查源文件、转换日志或文件是否能够打开。
- 标题、基本信息、图注、表格单元格、公式和正文等语义不同的段落必须使用可识别样式或显式格式；对交付关键属性不得只依赖模板默认值。
- 图注应直接设置居中和零缩进；表格单元格内所有段落应直接清除首行及左右缩进；姓名、版本、联系人等基本信息行应按模板直接设置对齐和缩进。
- 不能假定不同转换器使用相同样式名。例如图注可能表现为 `Caption`、`Image Caption` 或本地化名称；校验应结合段落语义、样式和直接格式，而不是只匹配一个英文样式名。
- 公式必须在最终页面尺寸下清晰、完整且与正文基线协调；原始标记、代码块式降级结果或无法辨认的位图不得作为无提示的定稿结果。
- 自动化检查至少覆盖关键段落的对齐和缩进、图片和公式是否存在、表格是否越界；视觉检查至少覆盖裁切、遮挡、分页孤行、字号和实际可读性。

如果交付模板明确规定不同版式，可以按模板调整，但仍须对最终文件执行同等强度的结构与视觉验证，并记录例外。

## 文档质量门禁

提交或合并前按项目风险执行：

1. 检查内部链接、目录索引和引用文件是否存在。
2. 验证命令、路径、配置名、版本和默认地址。
3. 按文档描述完成一次快速启动或相关操作验证。
4. 检查示例是否脱敏，是否混入本机路径、临时文件或生产信息。
5. 标记过期文档，明确替代文档或删除计划。
6. 对部署、迁移和回滚文档，确认步骤顺序、前置条件、验收信号和失败处理。
7. 对可编辑文档制品，检查最终文件的段落属性并逐页渲染复核，不以源文件或转换成功替代成品验收。

关键项目可将 Markdown 链接检查、拼写检查、示例构建和文档生成纳入 CI；不能因为自动检查通过就跳过内容与实际运行验证。
