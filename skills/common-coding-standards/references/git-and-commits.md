# Git 提交、分支与变更记录

本规范提供跨项目的默认 Git 约束。项目已有并经过团队确认的约定优先；如果采用不同流程，应在项目贡献指南中明确说明。

## 提交信息

### 默认格式

中文项目默认使用：

```text
<类型>(<范围>): <动作摘要>
```

示例：

```text
新增(试验设计): 支持指标智能设计
修复(认证): 修复令牌过期后的重复刷新
重构(后端): 按蓝图拆分接口注册
测试(算法): 增加边界样本校验
```

约束：

- `类型`使用统一词汇：`新增`、`修复`、`重构`、`优化`、`文档`、`测试`、`构建`、`工具`、`回滚`。
- `范围`写受影响的模块、领域或子系统；无法合理归类时可省略括号。
- `动作摘要`使用动词开头，说明完成了什么，不写“修改了一些问题”这类空泛描述。
- 摘要保持简短，建议不超过 72 个字符；不以句号结尾。
- 需要兼容处理的破坏性变更，在类型后增加 `!`，并在正文说明影响和迁移方案：`修复(接口)!: 调整响应字段`。
- 技术标识符、类名、接口名、配置键和命令保留原文，不为追求中文而翻译。

### 正文与脚注

摘要不足以解释决策时，空一行后补充正文，至少说明：

- 为什么要改，以及原行为或问题是什么。
- 改动影响哪些模块、接口、配置、数据或部署环境。
- 兼容、迁移、回滚和已知限制如何处理。

正文以事实和决策为主，不粘贴大段代码或审查过程。涉及任务系统时，在脚注关联任务号、Issue 或需求编号，例如 `Refs: PROJ-123`；修复问题可使用 `Fixes: PROJ-123`，具体关键字遵循项目平台约定。

## 提交粒度与历史

- 一个提交只围绕一个可描述、可验证的意图。
- 功能、无关格式化、全局重命名和大规模重构分开提交。
- 提交应尽量保持可构建、可测试和可回滚；如果中间提交无法独立运行，需在合并前整理或在说明中明确。
- 生成代码、锁文件和迁移文件只有在与该意图直接相关时才纳入。
- 不为“提交数量少”强行合并不同意图，也不为形式上的小提交拆散强相关改动。
- 回滚使用 `git revert` 生成新的 `回滚` 提交，不改写共享分支历史。

## 分支模型

除非项目明确采用 trunk-based 等其他模型，默认约定如下：

| 分支 | 用途 | 约束 |
| --- | --- | --- |
| `main` | 可发布或生产基线 | 受保护，禁止直接推送 |
| `develop` | 集成开发基线 | 通过合并请求进入，保持可集成 |
| `feature/*` | 新功能 | 从集成基线创建，完成后及时合并和删除 |
| `fix/*` | 普通缺陷修复 | 只包含一个问题的修复 |
| `refactor/*` | 结构重构 | 不夹带无关功能变化 |
| `release/*` | 发布准备 | 只做稳定性、版本和发布相关修改 |
| `hotfix/*` | 生产紧急修复 | 最小变更，修复后同步所有受影响基线 |
| `docs/*`、`test/*`、`chore/*` | 文档、测试和工程维护 | 不承载未声明的业务功能 |

项目若只有单一主干，可保留 `main` 并使用短生命周期工作分支；不要为了形式引入 `develop`。

## 分支命名

默认格式：

```text
<类型>/<任务号>-<简短描述>
```

示例：

```text
feature/PROJ-123-metric-design
fix/PROJ-456-token-refresh
refactor/PROJ-789-flask-blueprints
```

命名规则：

- 类型使用小写 ASCII：`feature`、`fix`、`refactor`、`release`、`hotfix`、`docs`、`test`、`chore`。
- 有任务系统时优先包含任务号；没有任务号时使用准确、可搜索的短描述。
- 描述使用小写 kebab-case，不使用空格、中文、特殊符号、随机字符串或个人姓名。
- 分支名表达目标，不写 `tmp`、`test2`、`new`、`最后版本` 等无信息名称。
- 分支保持短小，建议总长度不超过 60 个字符；避免嵌套过深。
- 同一分支只承载一个主题；发现主题发生变化时新建分支。

## 生命周期与协作

- 从最新的目标基线创建分支，长期分支定期同步，减少大规模冲突。
- 工作分支短生命周期使用完即删除；发布、维护和长期支持分支必须有负责人和退出条件。
- `main`、`develop`、`release/*` 等共享分支必须通过合并请求和 CI 门禁进入，禁止直接推送或绕过检查。
- 不改写已推送且被他人使用的共享分支历史。个人未发布分支需要整理历史时，可使用 rebase；强制推送必须使用 `--force-with-lease` 并确认没有覆盖他人提交。
- 合并前由作者解决冲突并重新验证，不在合并界面盲目接受一侧版本。
- 合并请求应说明变更摘要、关联任务、验证命令、兼容/迁移策略、已知风险和发布注意事项。

## 合并与发布

- 默认使用项目统一的合并方式；短生命周期功能分支可采用 squash merge，确保目标分支保留单一意图提交。
- 不同团队或项目若需要保留分支拓扑，可采用 merge commit，但必须避免重复合并和无意义的合并提交。
- 发布标签使用项目既定版本规则；采用语义化版本时使用 `vMAJOR.MINOR.PATCH`，不移动或覆盖已发布标签。
- 发布记录至少关联版本、提交或制品、变更摘要、迁移步骤、回滚方式和已知风险。

## 提交前检查

提交前至少检查：

1. `git status`：确认目标文件和未跟踪文件。
2. `git diff` 及暂存区 diff：确认没有无关修改、调试输出或误删。
3. 敏感文件、密钥、个人数据、缓存、构建产物和本机生成文件。
4. `git diff --check`：检查空白和冲突标记。
5. 与改动匹配的格式化、静态检查、编译、测试和构建。
6. 破坏性 API、配置、数据库或数据格式变化的兼容和迁移说明。

检查失败时不得通过删除测试、关闭门禁或隐藏错误来制造“通过”。

## 不可违背的边界

- 不修改或覆盖他人未提交的工作。
- 不提交密钥、Token、个人数据、构建产物、临时文件、调试代码或未经审查的在线资源。
- 不将提交信息当作审查报告；详细风险、验证结果和遗留问题应在合并请求或交付记录中补充。
- 分支命名、合并策略和发布标签若与本规范不同，必须在项目贡献指南中写明适用范围和原因。
