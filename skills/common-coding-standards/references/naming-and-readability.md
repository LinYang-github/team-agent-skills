# 命名与可读性

## 命名原则

- 名称表达职责、领域含义或状态，不使用无法区分的 data、temp、obj、handle、utils2 等名称。
- 布尔值使用 is、has、can、should 等能表达状态或能力的前缀；函数名使用动词，查询和修改动作在名称上可区分。
- 缩写只使用项目和领域中已约定的缩写；同一概念在不同模块中不得随意更换叫法。
- 文件、模块、类、函数和变量保持与所属层级一致的命名粒度，不用名称掩盖职责过多。

## 结构原则

- 一个函数或方法围绕一个可描述的职责组织；复杂流程拆成有名字的阶段，避免深层嵌套。
- 优先使用早返回、清晰的数据流和小范围状态，减少隐式全局变量和跨层副作用。
- 重复代码达到稳定复用场景后再抽象；抽象必须有清晰输入、输出、错误和生命周期。
- 复杂度、文件长度和参数数量达到项目阈值时，优先拆分职责而不是继续添加条件分支。

## 验收

- 新成员能通过名称和结构理解主要流程，不需要先阅读所有实现细节。
- 代码审查能指出每个模块的所有权、输入、输出和副作用。
- 变量重命名、模块移动和抽象没有改变公开行为；行为变化必须单独记录和测试。
