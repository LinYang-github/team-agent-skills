# 配置、交付形态、密钥与依赖

## 配置和密钥

- 配置通过环境、受控配置文件或依赖注入提供，不硬编码地址、账号、密码、Token、证书和密钥。
- 区分开发、测试、预发布和生产配置；必填配置缺失时快速失败，并指出变量名和安全的修复方向。
- 配置字段有类型、默认值、合法范围、来源和敏感等级；不把整份未校验配置对象透传给业务模块。
- 示例配置使用占位符和假数据，提交前检查密钥、个人数据、生产地址和本地路径。

## 配置分层与命令行覆盖

- 用户可以调整的运行配置与软件内部配置必须分开维护。内部配置随软件制品发布并由程序管理；用户配置使用独立文件或独立配置源，升级、覆盖安装和回滚不得静默改写。
- 监听地址、服务端口、数据目录、日志目录、外部服务地址和其他允许现场调整的非敏感配置，应提供稳定的命令行参数；适用时至少提供 `--config`、`--host`、`--port` 和 `--help`。
- 同一配置项只能有一个最终解析入口，优先级统一为“命令行参数 > 环境变量 > 用户配置 > 软件内部默认值”；启动日志可输出脱敏后的生效来源和值，不能让调用方猜测实际采用了哪一层。
- 未知参数、非法值、端口冲突和必填项缺失应在启动阶段快速失败，并给出参数名、来源和可操作的修复信息。
- 密码、Token、证书私钥等敏感值不得因“全部支持命令行”而进入进程参数或 Shell 历史；通过受控配置文件、环境注入或密钥管理机制提供，并在日志与诊断输出中脱敏。
- 配置格式、参数名、默认值或优先级发生变化时，应提供兼容、迁移和回滚说明；自动生成的示例配置与当前版本保持一致。

## 前后端一体化交付

- 同时包含浏览器前端和后端服务的软件，生产环境默认形成统一交付单元：前端 `dist` 与后端制品共同打包、安装、升级和回滚，不作为两套互不关联的软件分别交付。
- 前端 `dist` 可以由后端进程直接托管，也可以由随软件交付的 Nginx 等 Web 服务器托管；具体方式由项目部署方案决定，不由前端编码规范预设，但必须有自动化装配、启动和验证入口。
- 生产制品不得依赖前端开发服务器、开发代理或开发者本机路径；从空目录安装或解压后，应通过正式软件启动入口完成页面和 API 访问验证。
- API、静态资源、下载地址和前端路由使用明确且不冲突的路径边界；单页应用的 history fallback 不得吞掉 API 404、鉴权错误、文件下载或健康检查路径。
- 前端和后端版本、构建标识及资源清单保持一致，后端升级或回滚时同步切换配套前端资源，避免新旧资源混用。
- 对外服务入口、端口以及必要的内部代理端口由部署层统一管理，并通过用户配置和命令行覆盖；前端不得维护一套写死的生产端口配置，接口地址优先使用同源相对路径或受控运行时配置。

## 单服务部署约束

### 目录与读写边界

- 程序文件和内置资源默认只读；用户配置、业务数据、日志、缓存和临时文件使用职责明确的独立目录，升级或覆盖安装不得将运行时文件写回程序目录。
- 服务不得依赖启动时的当前工作目录、开发者主目录或源码树路径；所有运行路径通过统一的应用根目录、系统标准目录或显式配置解析。
- 每个目录明确创建时机、权限、容量、清理和备份策略；进程只获得完成职责所需的最小读写权限。

### 端口与网络约束

- 监听地址和端口不得硬编码，应通过用户配置和命令行覆盖；生产环境不得在端口冲突后静默选择随机端口，必须快速失败并指出冲突项。
- 监听范围必须显式：从本机地址扩大到全部网卡属于部署决策，不能因框架默认值意外暴露服务；内部管理端口默认不对外开放。
- 对外协议、端口、路径、TLS、代理关系和防火墙要求应可查询、可验证；同一进程的健康检查、管理接口和业务接口必须有清晰的访问边界。

### 升级与回滚

- 升级前检查目标版本、用户配置、数据结构和依赖兼容性；需要迁移时先备份并记录恢复点，不允许在无恢复路径时直接覆盖有效版本。
- 程序替换和配置迁移应尽量原子化；任一步失败都不得留下新旧文件混用、配置半迁移或服务状态不明的中间状态。
- 安装、升级和回滚脚本应可重复执行并保留明确退出码；不可逆的数据变更必须显式说明，并提供经过验证的前向修复或恢复方案。

### 健康检查与故障退出

- 进程存在不等于服务健康。服务应提供可自动判断的存活和就绪信号；就绪检查覆盖启动必需资源，但不得泄露敏感配置和内部诊断细节。
- 配置非法、端口冲突、关键资源缺失或必要依赖不可用时，应在有界等待后以非零状态退出，不得保持“进程存活但服务不可用”的假启动状态。
- 停止和重启应支持优雅退出，停止接收新任务并在限定时间内释放端口、文件、锁、线程和子进程；超时后再由部署层执行受控终止。

### 离线与受限环境

- 最终制品应包含目标环境运行所需的依赖、资源、配置模板和必要工具；安装、启动、核心功能和故障恢复不得临时访问公网下载内容。
- 制品清单应标明版本、目标操作系统与架构、运行时依赖、文件校验值和第三方许可证，便于离线核验完整性和来源。
- 发布前应在接近目标环境的干净、断网条件下完成安装、启动、配置覆盖、核心流程、重启和卸载或回滚验证，并记录实际结果。

## 依赖和资源

- 依赖来源、版本、许可证和安全状态可追踪；锁文件或等价机制纳入版本控制。
- 生产构建默认不依赖 CDN、远程脚本、远程字体、远程图片或未锁定的在线包；资源优先随制品交付并支持离线复现。
- 升级、替换或删除核心依赖前，验证公开 API、构建、测试、性能和许可证影响。
- 第三方库不能绕过项目的鉴权、错误、日志、配置和安全边界；不直接复制无法确认来源的代码。
