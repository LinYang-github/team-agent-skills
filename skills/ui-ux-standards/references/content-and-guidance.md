# 界面文案、术语与帮助规范

本文件统一桌面端企业应用中的业务术语、标题、标签、按钮、状态、错误文案和帮助表达。它只规定界面如何表达已经确定的业务含义，不替代业务词汇表、错误码设计、日志、监控、权限或安全规范。

## 基本原则

- 使用用户完成任务时采用的领域语言，不直接暴露接口名、数据库字段、组件名、状态枚举和开发缩写。
- 文案应准确、克制、可执行，适合长期值守和专业操作；不使用营销话术、卖萌表达和无意义的情绪安抚。
- 同一概念在一个产品内只使用一个主称谓；不同概念不能为追求简短被合并为同一词。
- 标题、字段、按钮、状态和错误各自承担一种职责，不用大段说明补救含义模糊的控件。
- 用户首先需要知道“发生了什么、影响什么、下一步是什么”，技术诊断放在次级详情或受控支持入口。

## 术语治理

- 每个项目应以已经确认的业务词汇表、产品术语或领域规范作为用语来源；UI 技能不预设“服务/应用”“想定/方案”等具体选词。
- 同义词选择一项作为主称谓，旧称、缩写或别名仅在迁移、搜索和首次解释时出现。
- 首次出现的专业缩写提供全称或可发现解释；用户已经高频使用且无歧义的行业缩写不机械展开。
- 不把不同层级对象使用同一名称，例如模块、任务、方案和实例应按真实关系区分。
- 状态名称描述业务事实，如“待执行”“执行中”“已中止”，不使用内部状态值或开发流程词。
- 正式行业标准已经定义的颜色、图形、术语或符号，应由项目或领域规范确认后映射到界面；不能凭“军工惯例”写入通用技能。

### 术语一致性检查

- 导航、页面标题、按钮、表格列、筛选、弹窗和帮助中是否使用同一称谓。
- 单复数、动作和对象是否一致，例如“新建任务”后不突然改称“创建作业”。
- 同一个动词是否保持同一结果，例如“移除”不能在一处表示解除关联、另一处表示永久删除。
- 用户可见文本是否避开 API 路径、变量名、数据库表名、英文枚举和未经解释的缩写。

## 标题与标签

- 页面标题直接描述当前任务或对象，避免“管理中心”“功能页面”等空泛名称。
- 区块标题说明内容类别，不重复页面标题；能通过布局和字段直接理解时不增加装饰性标题。
- 字段标签使用名词或短语，不把完整操作说明塞进标签。
- 单位靠近数值或输入控件，不能只写在帮助文档或 Tooltip 中。
- 占位文本仅提供输入示例或格式提示，不代替标签、默认值和当前值。
- 副标题只补充作用域、状态、限制或下一步，不改写标题含义。

## 按钮与操作文案

- 按钮使用明确动词或“动词＋对象”，如“保存”“删除指标”“重新加载”“查看详情”。
- 不用“确定”“好的”“提交一下”“执行操作”等模糊词代替真实动作；纯信息弹窗可使用“关闭”或“知道了”。
- 同一动作在页面按钮、菜单、快捷键提示和确认弹窗中使用同一动词。
- 危险按钮直接说明动作，如“删除”“覆盖”“终止”，不能使用普通“确认”掩盖风险。
- 取消类操作按实际含义使用“取消”“关闭”“返回”“放弃修改”，不要把不同后果都写成“返回”。
- 需要等待的动作保持原按钮文案并增加加载状态，不在“保存中…”“正在保存”之间频繁改变按钮宽度。

## 状态与空状态文案

- 状态名称描述当前事实，不用“正常”“异常”概括所有情况；当系统已经定义具体状态时，界面应展示可理解名称。
- 空数据、无搜索结果、未配置、无权限和加载失败分别表达，不统一写成“暂无数据”。
- 空状态按“当前状态＋原因或范围＋可用下一步”组织；没有可执行下一步时不强行增加按钮。
- 正常后台加载、页面进入和数据读取不显示“加载成功”“已获取数据”等打扰性文案。
- 部分成功必须说明成功数量、失败数量和失败项的处理入口，不能只显示“操作完成”。

## 错误文案结构

错误文案优先包含：

    对象或动作 + 失败结果 + 已知原因或影响 + 可执行下一步

例如：

- “方案保存失败，请检查网络后重试。”
- “未找到所选指标，它可能已被删除。请刷新列表后重新选择。”
- “3 项任务未能启动，请查看失败项并重新提交。”

规则如下：

- 说明用户当前能确认的事实，不猜测未经系统确认的原因。
- 简短不等于省略关键信息；只写“失败”“错误”“异常”不合格。
- 优先使用可执行的正向指引，如“请输入 1～100 之间的数量”，但不机械禁止“未找到”“无法连接”等必要否定表达。
- 不直接展示 HTTP 状态码、异常堆栈、接口路径、数据库信息和开发者错误文本。
- 可以展示稳定的错误编号或跟踪编号，便于现场支持；编号不能成为唯一提示，也不能包含敏感信息。
- 技术详情进入受控的“查看详情”“复制错误编号”或日志/支持流程；不得把生产问题仅记录到浏览器 Console 后让用户无从反馈。
- 错误信息靠近问题发生位置；只有跨页面、异步或无法归属局部区域的错误才升级为全局反馈。
- 保留用户已输入内容、筛选、选中和滚动位置，修复后允许继续当前任务。

## 常见失败场景

下表给出表达结构，不要求后端一定提供对应能力；实际原因、重试和权限语义以系统契约为准。

| 场景 | 推荐表达 | 应提供的界面动作 |
| --- | --- | --- |
| 请求超时 | “请求超时，请重试。” | 重试；长任务可查看状态 |
| 网络不可用 | “网络连接不可用，请检查连接后重试。” | 重试；保留当前输入 |
| 服务暂时不可用 | “服务暂时不可用，请稍后重试。” | 重试或返回安全位置 |
| 页面不存在 | “页面不存在或已被移除。” | 返回上一级或工作入口 |
| 对象不存在 | “未找到该对象，它可能已被删除或变更。” | 刷新、重新选择 |
| 权限不足 | “当前账号无权执行此操作。” | 查看权限说明或返回 |
| 数据冲突 | “数据已被其他操作更新，请刷新后检查差异。” | 刷新、比较或重新编辑 |
| 校验失败 | “请输入符合范围或格式的值。” | 聚焦到字段并保留输入 |
| 部分成功 | “已完成 7 项，3 项失败。” | 查看失败项、重试失败项 |
| 不可恢复失败 | “任务未能完成，错误编号：XXXX。” | 复制编号、联系支持或返回 |

- “页面开小差”“系统累了”“温馨提示”等拟人化或消费产品表达不作为企业桌面系统默认文案。
- “系统繁忙”只有在系统确实确认过载或排队时使用，不能代替所有服务端错误。
- 404 对页面、对象和接口的含义不同，界面应根据用户任务翻译，不能统一写成“请求地址无效”。
- 登录错误文案需兼顾安全和账号枚举风险，应由鉴权规范确认；UI 技能不固定为“密码错误”。

## 图标与现实世界匹配

- 图标采用项目统一图标库和用户熟悉的行业惯例，优先清晰、稳定和可区分，不要求机械模仿真实物体。
- 高度抽象、低频或危险操作不能只靠图标；保留文字、Tooltip 或确认说明。
- 终端、画布、仪表、时间线等专业控件可以借鉴现实工具的操作模型，但不为了拟真牺牲可访问性、主题适配和任务效率。
- 图标名称、文字标签和实际动作保持一致，不能用相似图形表达不同危险程度。

## 帮助梯度

专业系统不以“无需文档”为目标，而以“常用任务无需离开当前上下文，复杂知识有可发现帮助”为目标。

帮助按以下优先级提供：

1. 清晰的标签、结构和默认值。
2. 字段附近的格式、范围和影响说明。
3. Tooltip、示例、空状态和一次性引导。
4. 当前步骤或页面的上下文帮助。
5. 可搜索、可维护的完整帮助文档。

- 能通过更清晰标签、默认值或结构解决的问题，不先增加 Tooltip 和长说明。
- 一次性引导只用于首次出现且不易从界面理解的能力，用户应能跳过并重新查看。
- Tooltip 只承载短说明、名称和快捷键，不放关键业务规则和长段落。
- 复杂流程、专业模型、应急操作、正式制度和低频高风险任务应保留完整文档或操作规程入口。
- 帮助入口与当前页面、步骤或对象关联，避免只跳转到无上下文的文档首页。
- 帮助内容随产品版本维护；过期帮助比没有帮助更危险。

## 边界与工程职责

- 本文件规定用户可见结果，不规定前端请求拦截器、错误对象、重试算法和状态管理实现。
- Console 输出、日志级别、错误上报、脱敏、跟踪编号生成和生产环境诊断遵循 frontend-coding-standard 与 common-coding-standards。
- 前端校验用于即时反馈和减少误操作，后端仍负责权威校验；UI 技能不把前端校验当作安全边界。
- 撤销、回收站、模板、自动填充和通知中心是否存在属于产品能力；当系统提供这些能力时，界面按本规范清晰表达。

## 验收清单

1. 是否使用用户领域语言，并以项目业务词汇表而非开发术语为来源。
2. 同一概念、动作和状态是否在导航、页面、表格、弹窗和帮助中一致。
3. 标题、标签、按钮和状态是否各自清楚，没有依赖长说明补救模糊命名。
4. 错误是否说明对象、结果、已知原因或影响以及下一步，而不是只显示代码或“操作失败”。
5. 技术详情是否通过受控支持入口提供，界面是否未泄露敏感信息或依赖 Console 作为唯一诊断。
6. 超时、不可用、未找到、无权限、冲突、校验和部分成功是否使用不同且准确的表达。
7. 文案是否保持专业、克制，避免拟人化、营销化和空泛“温馨提示”。
8. 帮助是否从清晰界面逐级增强，高风险和复杂任务是否仍有正式文档入口。
