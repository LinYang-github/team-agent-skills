# UI/UX 统一规范

## 目标

在不抹平项目品牌和业务差异的前提下，让多个前端项目拥有可识别、可复用、可验收的共同体验。技能负责 UI/UX 判断、页面结构、交互语义、视觉令牌和验收方式；工程目录、API、状态管理、测试策略和代码风格由 `frontend-coding-standard` 负责。

## 职责边界

本技能只规定“已经存在的业务能力如何被界面清晰表达”，不规定系统必须具备哪些业务能力，也不定义业务数据、告警等级、风险分类、权限模型、审计要求、密级规则、单位体系、AI 治理或离线策略。遇到这些领域时：

- 如果业务规则尚未确定，先指出需要业务或系统规范确认，不用 UI 习惯替代业务决策。
- 如果系统已经提供相关能力，只规范其信息层级、状态表达、操作反馈、可发现性和主题适配。
- 使用“当系统提供……时，界面应……”的条件式表述，避免写成“系统必须……”。
- UI 改造不得修改接口、请求参数、响应字段、数据模型、路由、权限判断或业务处理逻辑。
- 未获明确授权时，不新增字段、标签、提示、按钮、流程、状态或业务能力。
- 深色主题下不得遗留白色组件、深色文字或默认灰色控件；主题覆盖应通过令牌和公共组件入口统一维护。

## 适用范围

当前本技能覆盖的前端项目均为桌面端，不做移动端适配，也不安排移动端测试；只有未来明确声明移动端范围时才另行扩展。

界面设计和实现默认不使用在线资源：不依赖 CDN、远程字体、远程图标、远程图片或在线脚本，优先使用项目内置并可随版本交付的资源；业务系统本身需要访问的后端 API 不属于此限制。

当用户要求以下任一事项时启用本技能：

- 新增或重构页面、导航、布局、表格、树、表单、弹窗、卡片和状态组件。
- 统一多个项目的颜色、字体、间距、圆角、边框、阴影、动效或浅色/深色模式。
- 评审截图、页面体验、组件一致性、信息层级、操作可发现性或视觉回归。
- 将 VibeCoding 产生的局部样式收敛为可复用的设计系统。

不要因为普通的业务逻辑、接口实现、后端改动或纯代码重构而自动扩展本技能的范围。

## 不可违背的原则

1. **先理解当前项目，再提出统一方案。** 优先读取入口、路由、布局、主题变量、公共组件和目标页面，不凭截图臆测全局。
2. **统一语义，不强行统一品牌。** 主色、密度、圆角和导航形态可以按项目调整，但状态含义、操作层级、可访问性和反馈机制必须一致。
3. **复用与单一来源优先。** 先查找已有组件、设计令牌和主题覆盖，再决定是否新增或抽取公共组件。基础数值由设计令牌定义，组件规格集中映射，页面不重复创造相近值；不要为视觉改造贸然替换组件库。
4. **业务优先。** 保留用户熟悉的流程和领域术语；视觉改造不得隐藏、删除或改变业务操作。
5. **信息优先。** 减少装饰性边框和冗余说明，建立清晰的标题、上下文、主要操作、内容区和状态反馈层级。
6. **产品身份一致。** 浏览器标签页标题和图标属于产品壳的一部分，应与应用内产品身份保持一致，不交给各页面临时发挥。
7. **浅色与深色同等验收。** 任何颜色、阴影、边框和图表方案都必须在两种主题下保持足够对比度和层级。
8. **关键操作按风险恢复。** 优先使用撤销、保留输入和可恢复设计；不可逆、批量或高影响操作采用与风险匹配的确认，不使用浏览器原生提示。
9. **跨领域能力只做表达。** 告警、权限、数据元信息、风险和 AI 结果的业务定义由其他规范或产品决策负责，本技能只约束其界面表现。
10. **资源来源可控。** 视觉验收应基于仓库内或随构建产物交付的字体、图标、图片和样式，不把在线资源可用性当作页面成立的前提。
11. **业务视觉不交给浏览器决定。** 核心业务控件应使用统一组件表达尺寸、主题、状态、焦点和浮层；保留原生语义和系统级能力，但不直接暴露不可控的浏览器默认视觉表面。

## 决策优先级

用户当前明确要求
> 项目品牌与业务约束
> 项目已有组件库和主题变量
> 跨项目共享语义规范
> 本技能的默认建议
> UI 组件库的默认样式

当已有规则与本技能冲突时，记录冲突及取舍，不要静默覆盖项目约定。

### 现状、范围与验收基线

- 先区分“现状描述”和“本次要求”。“当前只验收浅色主题”“现有页面依赖 CDN”等陈述默认是待整改现状，不等于用户授权保留这些问题。
- “只授权视觉与交互整改”限定的是修改边界，不会取消双主题、离线资源、长文本不遮挡、状态完整等 UI/UX 验收要求，也不允许修改字段、流程和权限逻辑。
- 本技能的硬性验收边界是：不改变业务契约、文字与控件不重叠、已有双主题均可用、交付资源不依赖公网。一般的风格偏好和本轮范围不能被解释为这些问题已经合格。
- 用户若明确排除某项硬性验收，按其范围执行，但必须将该项标为“未验证/例外”，说明影响；不得把局部完成表述为整体符合规范。

## 默认主题基线

当项目没有提供现成品牌色或主题令牌时，默认使用企业蓝作为主色基线。企业蓝只表示本技能的可替换默认值，不覆盖项目已有品牌规范；一旦项目提供品牌色，应将其映射到同一套语义令牌，并保持主操作、当前导航、链接和选中态的语义一致。具体令牌见 [references/design-foundation.md](references/design-foundation.md)。

## 浏览器标签页与产品身份

浏览器标签页必须统一表达“当前页面 + 产品名”，默认格式为：

    当前页面 · 产品名

例如：

    方案管理 · 凌云平台

规则如下：

- 使用当前任务或页面名称，不使用营销口号、解释性长句或重复模块说明。
- 产品名使用产品壳的正式名称；如果项目同时有平台名和业务中心名，优先使用用户需要辨识的产品品牌，避免连续堆叠多个层级名称。
- 详情页可按需补充当前对象，但保持简短，例如“城市低空巡检方案 · 方案管理 · 凌云平台”；列表页、工作台和设置页不重复对象描述。
- 页面切换、路由切换或多标签状态变化时，标题应由路由/页面元信息统一更新，不在多个组件内分别拼接。
- 每个项目应提供产品图标 favicon，并优先复用应用壳中的品牌标志；没有正式图标时使用与产品主色和品牌标记一致的最小化图形，不使用 Vue/Vite/浏览器默认图标、emoji 或随机图标。
- favicon、页面标题、theme-color 和应用壳品牌标志应在浅色、深色和构建产物中保持一致；图标资源必须随项目交付，不依赖远程 URL。

详细的标题、图标和验收规则见 [references/page-patterns.md](references/page-patterns.md) 与 [references/review-checklist.md](references/review-checklist.md)。

## 工作模式

根据请求选择一种或组合以下模式，并在开始时简要说明：

### 审查

盘点页面结构、视觉令牌、组件使用、交互状态和主题表现，按严重程度输出问题：阻塞体验、明显不一致、可优化项。先给证据，再给建议。

### 设计

为新页面或改造页面确定用户任务、信息层级、页面壳、主要操作、状态反馈和主题策略。先画出结构关系，再决定具体组件。

### 实现

将已确认的 UI/UX 方案落到现有框架和组件库中，优先修改令牌和公共组件，避免页面内重复 CSS。只修改用户请求范围内的文件。

实现阶段只落实已确认的视觉与交互方案；具体组件选型、封装方式、无障碍属性、测试和代码组织遵循 `frontend-coding-standard`。本技能只验收组件语义、状态、主题和交互结果。

### 回归

检查浅色/深色、默认/悬停/聚焦/禁用/加载/异常状态，以及窄窗口、长文本、空数据和大数据量下的表现。必要时使用浏览器或截图验证。

## 标准工作流

1. **确定边界**：确认目标项目、页面、用户任务、主题，以及本次只做审查、设计还是实现。当前技能覆盖的项目默认沿用桌面端范围，不擅自增加移动端。
2. **建立基线**：读取项目适配信息和相关参考资料；检查技术栈、入口、路由、布局、主题变量、公共组件及目标页面。
3. **区分稳定规则与可调参数**：稳定规则包括操作层级、状态语义、反馈、对比度、组件职责、基础尺寸阶梯和圆角层级；可调参数包括品牌色、已明确的密度模式、导航方向和页面最大宽度。偏离默认组件规格必须说明项目基线或任务原因。
4. **识别跨领域依赖**：若涉及告警、权限、数据元信息、风险、单位精度或 AI，先确认业务规则是否已有；没有时记录为待确认项，不自行补充规则。
5. **提出最小改造方案**：优先令牌、公共组件和页面壳，其次才是局部样式；说明哪些内容保留、哪些内容统一、哪些内容暂不处理。
6. **执行与验证**：实现后检查默认、悬停、聚焦、禁用、选中、空状态和弹窗状态，并检查两个主题；运行项目已有的构建/测试命令；若无法运行，说明原因和替代验证。
7. **交付记录**：按“问题—决策—修改—验证—遗留风险”汇报，避免只说“已优化”。

## 军事软件适配原则

涉及军工、试验、装备、作战、仿真、态势、运维或管理后台时，默认采用“工作台优先、任务优先、长页面谨慎”的判断方式。工作台不是把所有内容塞进一屏，而是让用户在稳定的上下文中持续观察、判断和操作。需要阅读、填写或确认的连续内容才使用长页面；不要把互联网产品的巨型首屏、营销式卡片堆叠和无任务装饰带入业务系统。

这是一项领域适配，不是替代用户明确要求的布局。若当前项目已有成熟壳层或用户明确要求长页面，保留其合理部分并说明取舍。

## 输出契约

按当前模式给出足以推进工作的结论，不机械复述固定栏目。至少说明主要发现或设计决策、修改范围、浅色/深色与关键状态的实际验证结果，以及未验证项和业务待确认项。审查任务先列问题；实现任务先列改动与验证。

## 与 frontend-coding-standard 的边界

本技能可以指出“应抽取公共组件”“应使用主题变量”这类 UI 架构意图，但不规定命名、目录、TypeScript、API、状态管理、测试组织、提交格式或性能实现。这些工程规则由 `frontend-coding-standard` 承载，两项技能通过已确认的 UI/UX 方案和工程实现结果衔接。
