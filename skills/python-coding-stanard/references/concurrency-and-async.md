# 并发与异步

## 企业默认结论

- 并发设计必须明确任务所有者、数据所有者、取消方式、超时、背压和关闭顺序。
- I/O 密集型任务优先使用 `asyncio` 协程与 `asyncio.CancelledError` 管理可协作取消；CPU 密集型任务使用 `multiprocessing` 或 `concurrent.futures`。
- 禁止把 `threading.Thread(daemon=True)` 作为规避 `join` 的手段。仅进程级基础设施且生命周期被严格证明时允许例外，并记录退出行为。
- 优先使用不可变数据、消息传递、`queue.Queue`/`asyncio.Queue` 和所有权转移；共享可变状态是受控例外。
- 工作队列、线程池、缓存和生产消费通道必须有界，并定义满载策略。
- GIL 限制 CPython 多线程 CPU 并行；CPU 密集并行使用 `multiprocessing`，不依赖线程突破 GIL。

## asyncio 基线

- 异步 I/O、网络、数据库和文件操作默认 `async`/`await`；不使用同步阻塞伪装异步。
- 异步函数返回 `Coroutine`/`Task`/`Future`；`Task` 通过 `asyncio.create_task` 创建。
- 所有可取消的异步操作响应 `asyncio.CancelledError`；不允许忽略取消。
- 异步方法命名以 `async` 或不特殊后缀（遵循框架约定）。
- 不使用 `asyncio.run_until_complete` 阻塞事件循环；入口使用 `asyncio.run(main())`。
- 异步闭包谨慎捕获 `self`；必须证明任务完成早于对象释放，或使用弱引用/取消。
- `asyncio.to_thread`/`run_in_executor` 用于将阻塞调用移出事件循环，不直接阻塞循环。

## Task 与线程生命周期

- 创建 `asyncio.Task` 或 `threading.Thread` 的组件负责 `cancel`/`join`，不把生命周期责任隐式转交给调用者。
- 不直接散布 `threading.Thread`；通过拥有型组件、执行器或线程池集中管理名称、数量、优先级、异常和关闭。
- 线程入口设置必要的名称和上下文，并建立异常屏障；任何异常都不能逃逸 `Thread.run`。
- 捕获到异步任务中的对象必须保证任务完成前有效；优先按值捕获不可变数据或转移所有权。
- `asyncio.create_task` 创建的任务必须存储引用，否则可能被 GC 回收；未引用任务异常可能被静默丢弃。
- 禁止无保护地捕获 `self` 后让任务超越对象生命周期。使用受控所有权、`weakref` 检查、取消后等待，或把任务状态与对象分离。

## 有界执行与背压

- 线程池任务数量根据 CPU、阻塞特性和资源预算设定，不按请求、连接或数据项无限创建任务。
- `asyncio.Queue`/`queue.Queue` 必须配置 `maxsize`，并明确满载时阻塞、超时、拒绝、丢弃旧项或降级。
- 提交接口返回可观察结果，不能静默丢任务。
- 生产者速度可能超过消费者时，在设计阶段建立背压；不得依赖内存耗尽或队列饱和作为限流机制。
- 任务应具有合理粒度，避免过细调度成本或单个任务长期独占事件循环。

## 锁与临界区

- 使用 `with lock:`/`asyncio.Lock` 上下文管理锁，禁止手工 `acquire`/`release` 分散在控制流中。
- 临界区只包含保护共享状态所需的最小操作；锁内不执行不受控 I/O、阻塞等待、外部回调或 `await`（同步锁中）。
- 多把锁建立全局锁顺序；需要同时获取多把锁时优先一致顺序，避免死锁。
- 锁保护哪些数据必须在声明附近说明。共享状态和对应锁对象尽量封装在同一类型中。
- 不返回受锁保护对象的可变引用，使其在解锁后逃逸。
- `threading.RLock` 仅在确需重入时使用；可重入锁不是修复重入设计的默认方法，应优先消除隐式递归调用。
- `asyncio.Lock` 异步等待优先 `async with lock`；混合同步/异步锁易死锁。
- 锁对象使用专用实例，不锁定全局对象或不可变类型。

## Condition 与等待

- `threading.Condition` 始终与谓词配合使用，并在循环中检查条件，以处理虚假唤醒。
- 修改受保护状态与检查谓词使用同一锁；通知时机应保证等待方能够观察新状态。
- 所有可能无限等待的操作必须评估超时、取消和关闭唤醒机制。
- 超时和持续时长使用 `time.monotonic()`/`time.perf_counter()`；只有表示日历时间时才使用 `time.time()`。
- 等待返回后必须区分条件满足、超时、取消和关闭，不把它们折叠为模糊的 `False`。

## 原子与无锁代码

- CPython 的 GIL 保证字节码级原子性，但不保证复合操作原子性；`+=`/`x[i] = ...` 等仍可能交错。
- 优先使用 `queue.Queue`/`asyncio.Queue` 表达生产消费；仅在性能数据证明锁是瓶颈时采用无锁设计。
- 使用 `threading.Event`/`asyncio.Event` 表达状态信号，不依赖裸 `bool` 共享变量。
- `itertools`/`collections.deque` 等线程安全容器仅保证单操作原子，复合操作仍需锁。
- 无锁算法必须测试 ABA、回收、溢出和伪共享，并通过专门审查。

## 数据发布与共享

- 对象在发布给其他线程前必须完成初始化，并通过锁、`queue.Queue`、`asyncio.Queue` 或不可变快照传递。
- 优先发布不可变快照（`frozen dataclass`/`tuple`/`frozenset`）；更新通过构造新值后替换完成。
- 不并发访问普通可变容器，即使不同线程看似操作不同元素，除非文档保证且容器结构不会变化。
- 缓存、单例和延迟初始化使用 `functools.lru_cache` 或模块级初始化，不手写双重检查锁定。
- `multiprocessing.Manager`/`shared_memory` 用于进程间共享，需理解序列化和同步成本。
- 避免 false sharing；高频独立计数需要基准和布局检查后再使用对齐隔离。

## 取消与关闭

- 取消是协作协议。长循环、阻塞点和批处理边界定期检查 `CancelledError`/`threading.Event`。
- `asyncio.Task`/`Future` 负责 `cancel`/`close`，不把生命周期责任隐式转交。
- 关闭过程明确状态机：停止接收、请求取消、唤醒等待、排空或丢弃、等待完成、释放资源。
- `close`/`stop`/`shutdown` 应尽可能幂等，并允许从预期控制线程安全调用。
- 不在持锁状态 `join` 可能反向获取该锁的线程；关闭顺序要消除循环等待。
- 超时退出后不得遗留仍访问已销毁状态的后台任务。

## 验证要求

- 并发单元测试覆盖启动、正常完成、取消、超时、队满、关闭竞争和异常路径。
- 使用 `asyncio.Event`/`threading.Event`/`queue.Queue` 协调测试，不用任意 `asyncio.sleep` 猜测调度时机。
- 使用 `tracemalloc`、`gc` 和并发测试观察竞争。
- 对锁竞争、队列深度、任务延迟和拒绝量建立可观测指标，但不得输出敏感业务数据。
- 压力测试和长稳测试不能替代内存模型与生命周期审查。

## 审查清单

- 谁拥有 Task/Thread 和共享数据，何时结束？
- 队列和任务数是否有界，满载时会发生什么？
- 是否在持锁时 `await`、调用外部代码或执行 I/O？
- 是否存在对象先释放、回调后到达或取消后仍运行的路径？
- 每个 GIL 限制和无锁假设是否有明确证明与测试？
