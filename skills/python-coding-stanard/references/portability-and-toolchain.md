# 可移植性与工具链

## 企业默认结论

- 新项目默认使用 Python 3.11；采用更高版本特性前，必须验证全部目标解释器、依赖、分析工具和部署平台。
- 项目维护明确的支持矩阵：操作系统、架构、CPython/PyPy、构建类型和最低版本。
- 构建以命令行 `python -m build`/`uv` 和 `pyproject.toml` 为事实来源，IDE 只消费同一配置，不拥有独立隐式设置。
- 源码、配置和文本资源默认 UTF-8；路径使用 `pathlib.Path`，跨平台代码不手工拼接分隔符。
- 平台差异集中在适配层、`sys.platform`/`os.name` 和平台源文件，不让条件判断散布业务代码。
- 发布必须验证目标架构、动态依赖、符号、安装布局和离线运行，不以“测试通过”替代可交付性。

## 支持矩阵

- README 或工程文档列出受支持与仅开发验证的平台，避免把“理论可导入”当正式支持。
- 每个正式平台至少保留一种受支持 CPython 配置；关键库应在多 Python 版本上验证以发现非标准依赖。
- 明确 x86_64、arm64 等架构，不用模糊的 64 位代替架构描述。
- CPython、PyPy 和第三方依赖版本统一由 `.python-version`、锁文件或 `pyproject.toml requires-python` 管理，不写在个人 IDE 配置中。
- 升级解释器/依赖作为独立变更执行完整构建、测试、mypy 和发布包验证。
- 使用 `tox`/`nox`/GitHub Actions 矩阵管理多版本测试，不依赖本机多版本偶然可用。

## 解释器基线与警告

- 项目自有代码至少启用 ruff 全部 E/F 规则与 mypy `--strict`；第三方目标通过 `exclude` 隔离，不全局降低检查等级。
- 更严格 ruff 规则（B、C4、SIM、UP）根据代码库成熟度逐项启用；不得一次开启后用大范围 `noqa` 抵消。
- 项目自有代码 lint/类型检查视为错误；第三方与生成代码通过目标边界隔离。
- 不全局关闭某条规则。例外应缩小到具体文件、行或表达式，并解释版本、风险和移除条件。
- `# noqa`/`# type: ignore` 必须带规则代码，并登记负责人和清理条件。
- 编译选项通过 `pyproject.toml`/`ruff.toml`/`mypy.ini` 配置，不依赖命令行临时参数。

## 工具版本与统一入口

- ruff、mypy、pytest、coverage 和代码生成器记录支持版本或版本范围。
- `.python-version`/`pyproject.toml requires-python` 锁定解释器版本；CI 与开发机使用同一入口。
- 格式化、静态分析、测试、发布提供统一脚本或 `make`/`just` 目标，开发机与 CI 使用同一入口。
- 禁止依赖仅存在于某位开发者 shell、IDE 插件或用户主目录的隐藏设置。
- VS Code/PyCharm 使用同一 `pyproject.toml` 与 `ruff.toml`，不维护 IDE 专用配置。

## 路径、文件名与跨平台

- 路径统一使用 `pathlib.Path`/`os.path.join`；持续集成至少包含大小写敏感文件系统验证。
- 不在源码中硬编码绝对路径、用户目录和构建机目录。
- 使用 `pathlib.Path` 组合路径、查询属性和遍历目录，不用字符串替换模拟路径语义。
- 路径与文本之间的转换集中在平台边界；Windows 原生宽字符接口由适配层处理，业务层保持 UTF-8 契约。
- 不使用跨目录的多层相对导入；通过包结构和可安装模式建立依赖。
- 路径分隔符、换行符、大小写敏感和文件属性差异集中处理，不散落业务代码。

## 字符编码与文本

- Python 源码、`pyproject.toml`、配置、脚本和可控文本文件采用 UTF-8；源码默认 UTF-8（PEP 3120）。
- 对外文件和协议显式声明编码，读取时校验（`open(..., encoding="utf-8")`）；不依赖系统区域设置。
- Windows 控制台编码（cp936/cp1252）与 UTF-8 在适配层显式转换，转换失败必须可观察。
- 不以 ASCII 中转中文文本，不按字节截断 UTF-8 字符串，不把字符数与字节数混为一谈。
- 面向二进制数据使用 `bytes`/`bytearray`/`memoryview`，不借用字符串承载任意字节。
- `locale`/`gettext` 显式传递，不依赖系统区域格式化数字和日期。

## 平台抽象

- 不在公共领域接口暴露 `ctypes`/`cffi`/`os` 平台类型；平台类型只存在于适配实现。
- 不为兼容平台而在全局重新定义系统类型。
- 条件判断优先选择平台源文件和窄适配层；单个函数内大量 `if sys.platform ==` 通常应拆分实现。
- 使用标准库能力代替平台 API 时，先核实语义、错误行为和性能满足要求。
- 对字节序、对齐、整数宽度和符号性不作隐式假设；序列化使用 `struct` 明确格式。
- `sys.platform`（`win32`/`linux`/`darwin`）和 `os.name`（`nt`/`posix`）用于平台分发，不依赖 `platform.system()` 字符串匹配。

## 交叉编译与架构

- C 扩展构建使用 `cibuildwheel`/`manylinux` 容器，覆盖目标平台矩阵。
- 各架构 wheel 放入可识别的 PyPI 标签（`cp311-manylinux_x86_64`/`win_amd64`），不靠运行脚本临时猜测。
- `platform`/`platform.machine()` 用于检测架构，但运行时能力检测优先于静态架构判断。
- SIMD 和专用指令集通过 `numpy`/`array` 或运行时能力检测启用，并提供符合支持矩阵的回退路径。
- 不从 `ctypes.sizeof(c_void_p)` 推断完整 ABI；使用明确的能力检查。

## 子进程与运行时依赖

- 发布前检查 C 扩展架构、导出符号、未解析依赖和解释器版本。
- 可使用 `auditwheel`（Linux）、`delvewheel`（Windows）和 `otool`/`ldd` 检查动态依赖。
- 不对不可信二进制直接 `ctypes.CDLL` 加载；先验证来源和哈希。
- 运行时搜索路径通过 wheel 的 `RPATH`/`@loader_path` 或受控启动脚本解决；`LD_LIBRARY_PATH` 仅用于诊断。
- 禁止通过修改用户的 shell 启动文件修复应用依赖，部署不得污染个人环境。
- 明确哪些系统库由目标系统提供，哪些依赖随产品交付，并检查许可证和安全更新策略。

## 安装、打包与发布

- `python -m build`/`uv build` 规则定义源码分发、wheel、公共 API、配置模板、资源和许可证的目标位置。
- 发布包不包含源码树绝对路径、临时文件、测试密钥、开发配置和无关依赖。
- 包提供 `__version__`、构建标识和必要特性信息，便于现场诊断。
- 每个平台从干净虚拟环境安装并运行消费测试，验证包内导入关系而非源码树偶然路径。
- 调试符号（C 扩展）按交付策略分离并可与构建标识关联。
- 可复现构建控制时间戳、文件顺序、生成器输入和环境依赖；无法完全复现时记录剩余差异来源。

## 审查清单

- 支持矩阵是否明确到解释器、依赖、架构和构建模式？
- 新代码是否依赖大小写不敏感路径、系统区域格式或个人环境？
- 平台条件是否被限制在适配层和构建配置？
- 发布包的架构、运行时依赖、搜索路径和离线运行是否经过验证？
- 工具链升级和新语言特性是否覆盖全部目标环境？
