# 测试、构建与质量门禁

## 测试层级

- 纯函数、格式化、映射、校验、状态转换和错误解析优先单元测试，测试输入边界和失败路径。
- 组件测试关注用户可观察行为、事件、加载/错误/空状态和关键 props；避免只测试实现细节或私有变量。
- 端到端测试覆盖关键业务路径、路由守卫、真实请求契约和跨页面状态；不要把所有逻辑都堆进慢速 E2E。
- 测试名称描述行为和条件，不描述内部函数名；失败信息要能帮助定位。

## 变更与回归

- 修改类型、请求封装、路由、鉴权、共享 store、公共组件或包入口时，扩大回归范围。
- 修改纯局部样式或页面文案时，运行相关组件测试、构建或浏览器检查即可，但必须说明范围。
- 网络、时间、随机数、存储和浏览器 API 在单元测试中显式 mock；不要依赖真实用户目录、线上服务或未清理的全局状态。
- E2E 使用隔离数据和可重复环境；不对生产或用户真实数据执行破坏性操作。

## 构建与类型

- 交付前运行受影响项目已有的类型检查、单元测试、构建和必要的 E2E 命令。
- TypeScript 项目优先使用 vue-tsc/tsc 和 Vite 构建共同验证；JavaScript 项目至少运行构建和已有测试。
- 关注构建警告、循环依赖、未使用导入、chunk 异常增大和 source map/环境变量泄漏。
- 修改共享包时先构建包，再验证应用消费；不能只验证某个源码路径。

## 依赖和配置

- 新增依赖前说明用途、体积、许可证、维护状态和已有替代方案；优先复用项目依赖。
- 依赖升级保持锁文件一致，按包和应用分别验证，不在无关改动中顺手升级大量依赖。
- 环境变量区分公开前端配置与服务端秘密；前端构建产物中的变量默认可被用户看到。
- 测试、构建和发布脚本应可在 README 或项目脚本中被发现；不要依赖个人机器上的隐含命令。

## 质量门禁

- 不通过删除测试、关闭类型检查、放宽错误处理或忽略构建警告来“修复”门禁。
- 暂时无法修复的历史问题可记录为基线并缩小影响范围；新增代码不得扩大问题。
- 最终交付说明实际运行过的命令和未运行的命令，避免笼统声称“已验证”。
