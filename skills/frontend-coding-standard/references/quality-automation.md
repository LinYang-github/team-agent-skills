# 代码质量与自动化门禁

本文件规定前端项目如何把工程约束变成可重复执行的检查。门禁应帮助定位问题和控制回归，不应通过删除测试、关闭类型检查或静默忽略错误来追求“全绿”。

## 格式、Lint 与类型

- 统一格式化工具、配置入口和忽略范围；格式化不承担业务重构，也不在无关改动中大规模改写历史文件。
- ESLint 或等价检查覆盖 Vue、TypeScript/JavaScript、import 边界、未使用代码、危险 API 和可疑副作用；规则例外必须有范围和原因。
- TypeScript 项目保持与项目基线一致的严格度；新增边界优先消除 `any`、隐式 `undefined` 和未校验外部数据。
- JavaScript 项目使用 JSDoc、运行时校验或逐步 TypeScript 化补足公共接口，不通过关闭检查掩盖不确定性。
- 类型、lint、格式和构建脚本在本地与 CI 使用同一入口或同一配置，避免“本地通过、CI 失败”。

## 依赖与变更审查

- 新增或升级依赖说明用途、体积、许可证、维护状态、漏洞和已有替代方案；锁文件与包管理器保持一致。
- 依赖升级分批进行并运行受影响包和真实应用验证，不在无关功能中顺手升级大量核心依赖。
- 检查重复依赖、异常体积、未使用依赖、深层导入和直接依赖内部 `dist` 的问题。
- 共享组件、类型、请求、路由、构建入口和包公开导出变化应触发扩大回归，而不是只运行当前页面测试。

## 自动化分层

- 纯函数、类型映射和错误解析在单元测试中快速验证；组件测试关注用户可观察行为；E2E 覆盖关键跨页面流程和真实契约。
- 路由、鉴权、公共组件、请求层、Mock、配置和错误边界变更时，明确新增或扩大的测试范围。
- 视觉和无障碍回归使用稳定的浏览器环境、隔离数据和可解释的基线；不要用大范围阈值放宽掩盖实际变化。
- 性能预算、包体积、依赖漏洞、语言 key、API 契约和构建产物检查按项目风险加入 CI，不要求所有项目一次性启用全部工具。
- 测试、构建和检查失败保留足够上下文；失败重试不能把非确定性测试伪装成通过。

## 本地与持续集成

- README 或项目脚本明确安装、开发、类型检查、lint、测试、构建和 E2E 命令；不依赖个人机器上的隐含全局命令。
- 提交前检查优先运行快速、确定的格式和静态检查；完整测试和构建在 CI 或交付前执行。
- CI 使用隔离数据、固定时区/语言、可控时间和随机种子，避免测试受用户目录、网络和执行顺序影响。
- 生成代码、API 类型、语言包和构建产物明确来源与更新命令，不手工编辑后又被脚本覆盖。
- 暂时无法修复的历史问题记录为基线并限制范围；新增代码不得扩大基线问题。

## 交付记录

最终交付至少记录：实际运行的命令、未运行的检查、失败原因、已知基线、依赖变更、兼容策略和后续风险。
