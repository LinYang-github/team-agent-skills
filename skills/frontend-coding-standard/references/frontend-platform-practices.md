# 前端平台实践

本文件补充 Vue 应用中容易被临时实现污染的运行时边界：路由、前端 Mock、样式和日志。它规定代码组织、环境隔离和可维护性，不替代 ui-ux-standards 对视觉语义和界面体验的判断。

## 路由与导航

### 路由记录

- 路由是应用导航和可恢复状态的公共契约；集中维护路由记录，按领域拆分路由模块，再由入口统一组装。
- 每条业务路由使用稳定且唯一的 `name`；路径表达资源和层级，不使用中文标题、随机 ID 或易变展示文案作为路径契约。
- `meta` 只保存标题、权限标识、布局、面包屑和缓存等导航元数据；不要把业务对象、接口响应或大块配置塞进路由记录。
- 页面、布局和重量级编辑器默认按路由懒加载；公共壳、错误页和首屏必需资源才保持同步加载。
- 嵌套路由反映布局和资源层级；不要为了复用一个页面片段建立没有导航意义的深层嵌套路由。

### 参数与状态

- 路径参数用于定位资源，查询参数用于筛选、排序、分页和可分享的视图状态；临时弹窗、草稿和敏感信息不要放入 URL。
- 对参数做类型转换、默认值和合法性校验；无效参数进入明确的空状态、错误页或重定向，不让组件各自猜测。
- 可从链接恢复、需要刷新保留或需要分享的状态优先进入 URL；仅跨页面共享但不适合公开的状态进入 store。
- 页面切换时清理订阅、请求、定时器和对象 URL；参数变化触发请求时取消或忽略旧结果。

### 守卫与失败路径

- 认证和权限守卫集中在路由基础设施，页面不重复执行 token 清理、登录跳转或权限判断。权限最终以后端校验为准，前端守卫只负责导航体验和减少无效请求。
- 守卫只做轻量、可预测的前置判断；需要大量业务数据的流程放在页面加载或领域服务中，避免导航被不可控请求长期阻塞。
- 统一处理未登录、无权限、未找到和加载失败；提供可恢复的返回、重新加载或切换上下文路径。
- 使用路由级错误边界或统一错误页承接异步组件加载失败，不在每个页面复制相同的兜底跳转。
- 修改路由、守卫、布局元数据或参数契约时，至少补充路由守卫和关键导航路径测试。

## 前端 Mock

### 设计原则

- Mock 位于 API 客户端边界，不放在页面、组件或 store 的业务分支中；业务代码应调用与真实后端一致的服务接口。
- 以 API 契约为源头定义 DTO、状态码、业务错误、分页、空数据和延迟语义；Mock 不得返回真实接口不会返回的“方便数据”。
- 优先采用请求拦截方案（例如项目已选定的 MSW 或等价机制），而不是在组件内写 `if (mock)` 或替换全局 `fetch`。
- Mock 必须显式启用，默认只在本地开发、契约测试或指定 E2E 场景生效；生产构建不得打包或启用 Mock 处理器。
- 开发 Mock 和 E2E Mock 分开管理：开发数据便于探索，E2E 数据必须确定、隔离、可重置并覆盖失败路径。

### 数据与生命周期

- 夹具使用工厂函数和最小必要字段生成，避免复制一大段不可维护 JSON；涉及时间、随机数和 ID 时提供可控种子或固定值。
- 为成功、空数据、校验失败、鉴权失效、网络异常、超时和分页边界准备独立场景；不要只 Mock 一个“全是成功”的世界。
- Mock 的延迟、取消和错误结构尽量接近真实请求；修复后端契约时同步更新类型、Mock 和测试，避免 Mock 长期掩盖接口漂移。
- 每个测试在结束时清理 handler、数据库/内存状态和全局副作用；测试不能依赖执行顺序或上一次测试留下的数据。
- 当真实后端已可用时，优先运行真实契约或集成验证；Mock 只能提高开发和测试确定性，不能替代后端联调。

## 样式管理

### 层次与作用域

- 样式按“全局基础层、主题/设计令牌层、组件层、页面层”组织；全局层只放 reset、字体、主题变量和少量布局工具。
- Vue 组件样式默认使用 `scoped` 或 CSS Modules；确需跨组件影响时，将规则放入明确的全局文件并注明作用范围。
- 不在页面中重复维护颜色、间距、圆角、阴影、层级和断点；使用项目设计令牌或 CSS 变量，缺少令牌时先补充令牌再扩散使用。
- 组件库覆盖集中在主题适配层或组件封装层，不用页面选择器和高权重链条到处打补丁。
- 避免 `:deep`、`!important`、行内样式和无限增长的选择器；必须使用时说明宿主边界和撤销条件。

### 主题与动态样式

- 明确亮色、暗色和系统偏好之间的优先级；主题切换只修改根节点变量或主题属性，不批量改写组件内联颜色。
- 动态值使用 CSS 变量或经过校验的受控 class；不要把用户输入直接拼进选择器、URL 或原始 CSS。
- 建立有限的 z-index 层级和断点策略；禁止页面各自发明任意数字导致遮罩、弹层和导航互相覆盖。
- 样式改动需要检查溢出、焦点态、禁用态、空/错误状态、亮暗主题以及构建后的 CSS 体积；视觉验收仍按 ui-ux-standards 执行。

## 日志与 `console`

### 输出边界

- 业务代码不直接散落 `console.log`、`console.warn` 或 `console.error`；通过基础设施提供的 logger 统一输出级别、结构和环境策略。
- 临时调试日志提交前必须删除，或转换为受控的 debug 日志并明确关闭条件；不要用日志替代错误状态、用户提示或测试断言。
- 在请求、路由、鉴权、全局错误和关键任务边界记录一次即可；避免在组件渲染、watch 循环或重复重试中刷屏。
- 级别至少区分 `debug`、`info`、`warn` 和 `error`。开发环境可启用 debug，生产默认关闭 debug/info，保留必要的 warn/error，并支持按环境配置。

### 内容与安全

- 日志使用结构化字段（事件名、模块、请求 ID、资源 ID、耗时、错误 code 等），不要依赖难以检索的长字符串拼接。
- 严禁输出 token、密码、密钥、Cookie、完整身份信息、完整请求体/响应体和未脱敏的敏感业务数据；必要时只记录哈希、摘要或白名单字段。
- 错误日志保留原始错误的 `cause` 或可定位上下文，但对用户展示的文案与内部诊断信息分离。
- 第三方 SDK、浏览器扩展和生产环境的日志策略应单独评估；不能因为关闭开发者工具就认为敏感信息已安全。
- 测试中对 logger 使用可断言的 mock，验证关键错误是否被记录以及敏感字段是否被过滤，不断言具体时间戳或环境噪声。

## 交付检查

涉及路由、Mock、样式或日志时，交付前至少确认：

1. 入口和依赖边界明确，没有把临时方案散落到页面。
2. 开发、测试、生产环境行为可区分，生产产物不包含未授权的 Mock 或 debug 输出。
3. 参数、错误、空状态、取消、刷新恢复和权限失效路径经过验证。
4. 主题变量、选择器作用域、层级和构建体积没有引入不可控的全局副作用。
5. 实际运行过的检查、测试和构建命令已记录，未运行的验证不作笼统声称。
