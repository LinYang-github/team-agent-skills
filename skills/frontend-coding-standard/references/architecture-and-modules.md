# 模块分层与工程结构

本文件规定代码组织和依赖方向，不规定页面的视觉布局。项目可以使用不同目录名称，但必须能解释每个模块的职责和依赖关系。

## 推荐分层

从低到高建议分为：

1. **基础工具**：日期、格式化、纯函数、类型辅助；不依赖 Vue、路由或业务。
2. **基础设施**：请求客户端、鉴权适配、日志、存储、运行时配置；只依赖基础工具和平台库。
3. **领域服务**：某个业务对象的 API、DTO 映射、领域类型和可复用查询；不依赖具体页面。
4. **状态模块**：跨页面或跨组件共享的 Pinia/store/composable；负责状态和动作，不承载所有视图细节。
5. **业务组件**：可复用的领域组件和交互单元；通过 props、事件或明确的 store 协作。
6. **页面与路由**：组合业务组件、加载页面数据、处理路由参数和页面级副作用。

依赖方向应从上层指向下层；下层不能导入页面、路由、具体视图或高层业务组件。跨层依赖确有必要时，先抽取接口、纯函数或适配器。

## 目录策略

- 以项目现有目录为基线，不为追求理论结构一次性搬迁全部文件。
- 新功能优先按领域或功能聚合，避免把一个功能的类型、API、状态和组件散落到无法定位的全局目录。
- 全局 components 只放真正跨领域复用的组件；领域组件放在对应功能或包内。
- utils 只放无状态、边界清晰的工具；请求、权限、业务转换和复杂状态不要全部塞进 utils。
- 页面文件负责组合和编排；复杂数据转换、异步流程和可测试规则应移到服务、composable 或纯函数。
- 路由元信息、权限元数据和页面标题集中定义，避免组件挂载后再隐式修正路由行为。

## 公共组件与抽象

- 先出现两个以上稳定且语义一致的使用场景，再考虑抽取公共模块；只复用样式不等于应该共享业务状态。
- 公共组件的 props、emits、slots 和返回值保持小而明确，不暴露底层实现细节。
- 不创建接收几十个配置项的万能组件；差异明显的场景拆成领域组件或组合小组件。
- 对外导出的模块保持稳定入口，内部文件可以重构；跨包使用时避免深层相对路径。

## 依赖与副作用

- 优先使用单向数据流；副作用集中在生命周期、composable、store 或服务边界。
- 订阅、定时器、WebSocket、事件监听、AbortController 和对象 URL 必须在失效时清理。
- 禁止模块导入时执行不可控的网络请求、页面跳转或全局修改，除非入口初始化明确需要并有测试覆盖。
- 检查循环依赖；遇到循环依赖时优先移动类型、抽取接口或引入适配层，而不是依赖导入顺序。

## 包和共享库

当项目包含 packages 或可构建库时：

- 共享包不得依赖具体业务应用的运行时状态。
- 包的公开导出、构建入口和类型产物保持明确；应用内部模块不要依赖 dist 目录。
- 先验证共享包构建，再验证至少一个真实应用消费路径。
- 包间版本和变更影响写入交付记录，避免只在某一个应用中修补契约。
