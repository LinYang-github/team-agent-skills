# API、鉴权、错误与状态

## 请求层

- 每个应用优先只有一个可配置的请求入口或少数按协议划分的客户端；页面不直接散落创建 Axios 实例或拼接基础地址。
- API 地址来自运行配置、环境变量或现有代理约定；开发、测试和生产地址不要硬编码在业务组件中。
- 请求层统一处理鉴权注入、超时、取消、响应解析、协议错误和网络错误；业务模块只处理领域结果。
- 二进制下载、流式响应和特殊协议可以有明确例外，但要在客户端接口中声明，不让调用方猜测返回形态。

## 契约与映射

- 区分后端 DTO、前端领域模型和表单模型；字段名称、可空性和枚举值在边界处转换。
- 不把后端原始响应对象直接传遍所有组件；由服务层或适配器整理为稳定结构。
- 兼容旧接口时集中处理旧格式，不在每个页面复制兼容分支。
- API 改动先确认调用方、错误码、空值和分页/排序约定，再修改类型和测试。

## 错误处理

- 区分网络错误、HTTP 错误、业务错误、鉴权失效、校验错误和取消请求；它们的恢复方式不同。
- 请求层可以转换错误，但不要默认在底层弹出所有提示，避免同一错误同时出现多个通知。由调用场景决定提示、内联错误、页面状态或静默处理。
- 错误对象保留稳定的 code、status、message 和原始上下文字段，便于测试和定位；展示文案在适当边界本地化。
- 401/会话失效遵循项目统一登出或刷新流程；不要在多个组件各自清 token、跳转和 reload。
- 日志不得包含 token、密码、密钥或完整敏感响应；生产日志使用结构化、可控级别和脱敏字段。

## 加载、并发与取消

- 异步请求明确 idle、loading、success、empty、error 和 stale 等实际需要的状态；不要用一个布尔值覆盖所有情况。
- 页面卸载、参数切换或新请求替代旧请求时，取消或忽略过期结果，避免旧响应覆盖新状态。
- 防止重复提交；需要重试时区分幂等请求和具有副作用的请求。
- 搜索、联想和筛选请求应考虑防抖、取消和结果顺序；不要让每一次按键都无控制地发请求。
- 缓存要说明失效条件和刷新策略；不以永久缓存掩盖接口或状态设计问题。

## 状态边界

- 组件状态只承载当前视图需要的临时数据；跨路由共享、用户上下文和可复用缓存进入 store 或服务层。
- 不把同一事实同时写入多个 store、组件和 localStorage；需要派生值时使用 computed/selectors。
- 路由参数、查询条件和分页状态是否进入 URL，应按可分享、可恢复和安全要求决定。
- 刷新、返回、切换租户/项目或权限失效后，状态要有明确恢复和清理策略。
