# 严重性与审查意见

## 严重性

| 等级 | 判断标准 | 交付要求 |
| --- | --- | --- |
| P0 | 灾难性数据破坏、远程利用、全量不可用或无法启动 | 立即阻断 |
| P1 | 高概率且高影响的功能、安全、数据完整性或发布问题 | 合并/发布前修复 |
| P2 | 在明确条件下触发的真实缺陷、兼容性问题或运行风险 | 当前变更优先修复 |
| P3 | 有证据的测试缺口、维护性或工程质量问题 | 可排期处理 |

严重性同时考虑触发概率、影响范围、可检测性、可恢复性和暴露面。

## 意见格式

```text
[P1] 回滚版本无法恢复迁移后的数据

位置：deploy/migrate.sql:42

触发条件：发布执行新字段迁移后，按现有回滚脚本恢复旧版本。
问题：回滚只替换应用制品，没有逆向迁移或兼容读取。
影响：旧版本启动失败，发布无法恢复。
证据：旧版本 schema 不包含新字段，启动查询未做兼容处理。
建议：采用先兼容后迁移的顺序，或提供经过验证的回滚/前向修复方案。
```

每条意见必须能回答：在哪里、何时触发、会造成什么后果、为什么确定、如何最小化修复。置信度不足时标记“待确认”，不要把假设写成缺陷。

## 降低误报

- 不报告无法到达的理论路径，除非它暴露出明显的安全或灾难性风险。
- 不把项目明确的产品行为当作缺陷。
- 不重复报告同一根因造成的多个表象；保留最能说明影响的定位。
- 不以“可以更优雅”为理由报告 P0/P1。
- 生成代码、第三方代码和构建产物只在其进入交付链或改变运行行为时审查。
