# 全项目工程审查

本模式用于评估项目整体，不依赖单次 diff。每个维度都必须基于仓库证据、构建结果、配置或运行文档；信息不足时明确假设，不用主观印象替代证据。

## 审查维度

### 1. 项目定位与边界

- 项目解决的问题、目标用户和核心场景是否清晰。
- 技术边界和非目标是否明确，是否存在功能膨胀或重复建设。
- 架构复杂度是否匹配项目规模、团队能力和变更频率。

### 2. 架构设计

- 模块职责、依赖方向和公共契约是否清晰。
- 是否存在循环依赖、反向依赖、共享可变状态或上帝模块。
- 新功能、新协议和替换实现的扩展点是否合理。

### 3. 代码组织与可读性

- 目录、命名、抽象边界和重复代码是否支持长期维护。
- 是否存在过长函数、过重对象、魔法值或无收益的过度抽象。

### 4. 错误处理、日志与可观测性

- 错误是否保留上下文并可恢复，是否存在吞错和不可诊断失败。
- 日志、指标、追踪、告警和关联标识是否支持线上定位。

### 5. 配置、环境与部署

- 配置、密钥、依赖和环境差异是否可管理、可审计、可回滚。
- 构建、启动、探活、优雅退出、发布和回滚路径是否清晰。

### 6. 稳定性与边界

- 并发、超时、重试、幂等、资源释放、容量和故障恢复是否有保护。

### 7. 可测试性

- 核心逻辑能否隔离测试，外部依赖是否可替换，测试是否覆盖关键失败路径。

### 8. 安全性

- 权限、输入、路径、命令、依赖、敏感数据和供应链风险是否受控。

### 9. 工程成熟度

- 新成员能否按文档构建、运行和验证。
- 是否具备质量门禁、版本记录、迁移策略、发布记录和责任边界。

## 阶段判断

结合项目规模、团队和运行环境，给出“原型/验证、可用内测、生产基础、规模化演进中”等阶段判断，并说明依据。不要仅以代码行数或文件数量判断成熟度。

## 发现排序

优先报告会导致数据损坏、无法发布、持续不可用、无法恢复或后续重构成本显著上升的问题；一般风格和偏好放在最后或不报告。
