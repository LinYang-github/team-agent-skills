# 架构演进分析

在全项目审查或用户明确要求时，假设业务规模、数据量、并发量、团队人数或模块数量扩大约 2～5 倍，分析最先暴露的限制。

至少回答：

- 哪些模块会成为吞吐、延迟、构建或发布瓶颈。
- 哪些模块职责过重，哪些公共包已经形成隐性耦合。
- 哪些数据结构、配置、接口或错误契约需要提前稳定。
- 哪些模块可以先通过接口、事件、端口适配器或独立包解耦。
- 哪些模块具备独立部署或替换价值，哪些不应过早拆分。
- 当前技术债的利息、触发条件、临界信号和建议处理窗口是什么。

建议按“现在必须做、近期应做、达到触发条件再做”分级。不要因为存在理论上的未来需求就建议拆分微服务；必须给出触发指标或组织原因。
