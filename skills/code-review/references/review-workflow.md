# 审查工作流与模式

## 模式选择

- **快速审查**：小范围、低风险修改；关注编译错误、明显逻辑回归、错误处理和测试失败。
- **标准审查**（默认）：覆盖行为、边界、安全、兼容性、测试、可观测性和维护风险。
- **风险审查**：涉及鉴权、敏感数据、并发、数据库迁移、公共 API/ABI、核心算法、基础设施或发布流程时使用。
- **回归审查**：针对已修复的意见重新检查触发路径、相关调用方和新回归，不重复已解决的问题。

## 上下文收集

先看 diff，再补充必要上下文。至少检查修改点的调用方/被调用方、数据结构或接口契约、相关测试和配置。对删除、重命名和迁移必须搜索旧符号和旧字段的全部引用。

## 多轮检查顺序

1. 行为正确性和边界条件。
2. 错误路径、重试、幂等、超时和恢复。
3. 权限、敏感数据和外部输入。
4. 生命周期、资源释放、并发和异步。
5. API/ABI、配置、数据库和依赖兼容性。
6. 性能、容量、日志、指标和追踪。
7. 测试充分性和可维护性。

风格和格式放在最后，且只有在会造成工具失败、误用或长期维护风险时才报告。

## 交付审查顺序

代码通过不代表可以交付。涉及构建或运行环境时，依次确认：

1. 能否在声明的环境中重复构建。
2. 构建产物是否完整、可识别、来源可追溯。
3. 配置和密钥是否由目标环境注入，默认值是否安全。
4. 启动、健康检查、优雅退出和依赖就绪顺序是否一致。
5. 数据迁移是否可预演、可观测、可回滚或有明确不可逆说明。
6. 发布策略是否限制影响面，失败后是否能恢复到已知版本。
7. 发布后是否有日志、指标、告警和验收信号。
