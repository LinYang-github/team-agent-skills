# 代码审查

## 技能定位

本技能负责“如何审查一次变更或一个项目并给出可信结论”，不是另一套语言编码规范。始终先读取 `common-coding-standards`；根据变更文件和风险，再按需读取 `frontend-coding-standard`、`go-coding-standards`、`cpp-coding-standard` 和 `ui-ux-standards`。

- `common-coding-standards`：跨语言的工程底线。
- 语言/框架技能：具体实现约束。
- `ui-ux-standards`：仅在界面视觉或交互变化时参与审查。
- 本技能：范围、基线、风险、证据、验证、严重性和报告。

## 默认授权边界

审查默认是只读操作：不修改代码、不提交、不推送、不发布评论、不批准合并，也不执行部署。只有用户明确要求修复、提交或发布时，才切换到相应流程；审查结论与实施动作应分开记录。

## 审查模式

根据用户目标选择模式，不要用全项目清单审查每个小改动：

- **变更审查**（默认）：针对 diff 检查功能、边界、兼容性和回归。
- **全项目工程审查**：在没有明确 diff 或用户要求评估项目整体时，检查项目定位、架构、代码组织、错误处理、配置部署、稳定性、可测试性、安全和工程成熟度。
- **部署交付审查**：聚焦构建、制品、环境、迁移、发布、回滚和发布后观测。
- **回归审查**：针对已修复意见检查原触发路径及新回归。

全项目审查和部署交付审查的详细清单仅在对应模式下读取。

## 审查对象与基线

先确认变更意图、验收标准和审查对象，再计算准确差异：

- 未提交修改：分别查看暂存、未暂存和未跟踪文件，避免漏审。
- 指定提交或范围：使用用户给出的精确提交边界。
- 分支审查：以当前分支与目标分支的合并基点为基线，不假定只有上一个提交。
- 部署审查：同时检查构建入口、产物、镜像/安装包、运行配置、基础设施脚本、迁移、健康检查、发布和回滚路径。

若范围或基线无法确定，应先说明假设和可能遗漏，不把不完整的 diff 当作完整审查。

## 标准工作流

1. 读取项目 `AGENTS.md`、README、构建/发布说明和局部规范。
2. 识别审查模式、变更类型、影响面和风险等级，决定采用快速、标准或风险审查。
3. 阅读修改代码及其调用方、接口契约、测试、配置、schema 和部署文件。
4. 依次检查正确性、异常与恢复、安全和数据边界、生命周期/并发、兼容性、性能、测试、日志与可观测性。
5. 对涉及交付的变更，额外检查构建可重复性、环境差异、配置注入、依赖与制品来源、迁移顺序、启动/探活/优雅退出、发布策略、回滚可行性和运行后观测。
6. 运行与风险相匹配的只读验证：测试、构建、lint、静态分析、制品检查或部署配置校验；如未运行，明确标记。
7. 仅报告有证据、可触发、可复现或足以阻断交付的实际问题；按严重程度排序。
8. 输出审查范围、发现、验证结果、未覆盖项和遗留风险。

## 审查意见门禁

- 每条可确认问题的标题必须以 `[P0]`、`[P1]`、`[P2]` 或 `[P3]` 开头；“严重”“高风险”“建议优化”等文字不能替代等级。
- 每条问题只描述一个根因，并同时给出紧凑位置、触发条件、实际影响、证据或推理、最小修复方向。
- 证据不足的内容标为待确认或遗留风险，不编造成问题；同一根因造成的多个表象合并报告。
- 没有可确认问题时明确说明，并列出未执行验证和剩余风险，不为了满足格式虚构 P 级问题。
- 输出前自检所有问题标题是否匹配 `[P0]`～`[P3]`；若仍使用“高/中/低”等自然语言等级，先转换再交付。

## 输出契约

每条问题遵循上述审查意见门禁。不要用格式偏好、泛化猜测或重复评论制造噪声。

普通变更审查推荐结论顺序：

1. 发现的问题（P0 至 P3）。
2. 已执行的验证及结果。
3. 未执行的检查、假设和遗留风险。
4. 合并/交付建议。

没有问题时应明确写“未发现当前范围内的可确认缺陷”，同时列出未覆盖的环境、数据或部署风险；不能将“没有发现”表述为“绝对没有风险”。全项目审查应额外给出阶段判断、优先级改进路线和架构演进建议。
