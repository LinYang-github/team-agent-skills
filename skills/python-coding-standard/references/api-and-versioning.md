# API 与版本兼容

## 企业默认结论

- 先明确交付的是源码接口、同解释器包接口，还是跨解释器、跨语言、长期稳定的接口；三者不能共用模糊承诺。
- 仅供同仓库构建的模块优先提供类型安全的 Python API；跨解释器、插件或长期稳定边界默认采用接口、DTO 和版本化数据结构。
- 公共 API 必须说明所有权、生命周期、可空性、线程安全、错误模型、单位、编码和兼容策略。
- 包默认通过 `__all__` 显式声明公共符号，仅暴露承诺的公共入口。
- 异常、内部可变状态和解释器特有类型不得跨越不受控 ABI/序列化边界。

## 区分 API 与版本

- API 兼容指已有调用方源码无需修改即可继续工作。
- 行为兼容指已有调用方无需修改即可保持相同可观察行为。
- 修改名称、签名、默认参数、异常类型和语义可能破坏 API。
- 修改可序列化字段、协议格式、导出符号和类型层次可能破坏序列化/行为兼容。
- 评审公共变更时必须分别给出 API 和行为影响，不用“向后兼容”笼统代替。

## 公共 Python API

- 公共模块自包含、依赖最小，不暴露内部目录、私有类型和非必要第三方类型。
- 参数与返回类型通过注解表达所有权和缺省语义；不得要求调用方猜测释放方法或有效期。
- 公共枚举保留未知值处理策略；新增枚举值时，调用方不应因穷尽匹配进入未定义行为。
- 接口的线程安全级别明确为线程兼容、实例可并发、只读可并发或完全线程安全。
- 不轻易在公共接口中暴露具体容器、`Task`、`Iterator` 和执行器；确需暴露时，将其视为长期契约。
- 公共函数的默认参数变化属于 API 变更，需纳入兼容性审查。

## 包版本与发布

- 包版本（`__version__`/`pyproject.toml [project].version`）遵循语义版本号（SemVer）。
- 主版本号递增表示破坏性变更，次版本号递增表示兼容新增，修订号递增表示兼容修正。
- `requires-python` 声明最低 Python 版本；提升最低版本属于破坏性变更。
- 包发布到 PyPI 或内部制品源前记录目标平台、Python 版本和依赖范围。
- `__all__` 用于限制公共 API 表面；未列入的符号视为内部实现。
- 弃用通过 `DeprecationWarning`/`FutureWarning` 标记，必须提供替代方案、迁移说明和移除版本。

## 稳定接口边界

- 使用 Protocol 和 DTO 导出稳定入口，采用版本化数据结构。
- DTO 携带版本字段；新增字段只追加，读取前检查调用方提供的结构版本。
- 明确字符串编码（UTF-8/UTF-16）、是否包含终止符、缓冲区容量、实际写入长度和截断行为。
- 内存由分配方释放。跨运行时返回动态内存时，必须提供同模块释放函数，或由调用方提供缓冲区。
- 不在边界传递 `Task`、`memoryview`、生成器、闭包和解释器特有对象。
- 导出函数捕获全部异常，返回稳定状态码；诊断信息通过显式错误查询或调用方缓冲区获取。
- 回调接口说明调用线程、是否可重入、调用时机、用户上下文生命周期和注销后的在途回调行为。

## 序列化与协议兼容

- 不通过 `pickle` 建立持久化和网络协议（不安全，跨版本不兼容）。
- 协议明确字节序、字段宽度、编码、对齐、版本、缺省值、未知字段和最大长度。
- 优先 `json`/`msgpack`/`protobuf` 等显式序列化器；自定义序列化集中处理，不散落业务代码。
- 解析所有外部数据时执行长度、范围、数量、递归深度和资源预算校验。
- 版本升级优先采用可忽略新增字段的扩展方式；字段删除、改义和复用编号属于破坏性变更。
- 可序列化类型默认不可变；可变状态不参与序列化，避免反序列化后状态不一致。
- `dataclass` 序列化通过显式 `asdict`/`astuple` 或专用库，不依赖 `__dict__` 直接落盘。

## 版本、弃用与插件握手

- 公共接口采用一致版本策略，区分兼容新增、行为修正和破坏性变更。
- 弃用使用 `warnings.warn(..., DeprecationWarning)` 标记，必须提供替代方案、迁移说明和移除版本；不能只加标记后无限保留。
- 插件加载首先完成版本、能力集和必要运行时条件握手，不直接假定兼容。
- 不兼容时返回清晰错误并拒绝加载，不尝试带病运行。
- `importlib` 插件隔离边界明确；不依赖全局 `sys.modules` 状态。

## C 扩展与 ABI

- C 扩展的 C API 版本、`PyTypeObject` 布局和方法表必须稳定；修改结构布局属于破坏性 ABI 变更。
- 跨 Python 版本的 C 扩展使用稳定 ABI（`Py_LIMITED_API`）或为每个版本构建。
- `ctypes`/`cffi` 不暴露 Python 对象到 C 边界；所有权转移必须明确。
- `ctypes`/`cffi` 调用约定、调用约定和符号可见性必须与目标库一致。
- 修改 C 扩展公共结构、函数签名和导出符号时，必须评估 ABI 影响并执行跨版本加载测试。

## 验证要求

- 公共模块在最小调用方工程中独立导入。
- 包执行导出符号检查、版本差异检查、跨版本加载和创建/销毁冒烟测试。
- 发布包至少在每个受支持 Python 版本和平台执行安装后消费测试，而不只验证源码树内构建。
- 兼容性测试保存上一受支持版本的包或协议样本作为基线。
- `__all__` 与实际导出符号一致性检查纳入 CI。

## 审查清单

- 当前边界需要源码兼容、同解释器行为兼容，还是跨解释器稳定接口？
- 谁创建和释放对象，字符串、缓冲区和回调能存活多久？
- 是否泄露了 `Task`、异常、内部可变状态或第三方实现细节？
- 此变更是否影响公共签名、序列化字段、C API 或运行时绑定？
- 是否有旧版本消费方和真实发布包的兼容性验证？
