# 测试与分析

## 企业默认结论

- 新建 Python 项目默认使用 pytest 编写单元与组件测试，使用 `pytest` 统一发现、执行、超时、标记和报告；项目已有成熟框架（unittest）时可保持一致，但必须接入 `pytest`。
- 每个可独立验证的模块或组件具有对应测试目录；测试不复制被测源码，通过导入被测包验证。
- CI 流水线启用 mypy（严格模式）与 ruff；并发代码另设并发测试流水线。
- 项目自有代码的 lint、类型检查和格式检查属于质量门禁；第三方和生成代码隔离处理。
- 覆盖率用于发现缺口，不以单一百分比替代边界、失败路径和风险验证。

## 测试分层

| 层级 | 关注点 | 默认要求 |
| --- | --- | --- |
| 单元测试 | 纯逻辑、状态转换、边界和错误路径 | 快速、隔离、确定性，可高频执行 |
| 组件测试 | 模块接口、异步协作、文件与适配器 | 使用真实组件，外部依赖受控 |
| 集成测试 | 子进程、数据库、进程、协议和系统接口 | 固定环境、显式超时、可重复清理 |
| 契约与兼容测试 | API、序列化和历史样本 | 覆盖旧版本消费方和异常输入 |
| 系统与安装测试 | 发布包、配置、启动、核心流程 | 从发布产物执行，不依赖源码树 |

- 测试重点覆盖边界值、空输入、超大输入、损坏数据、超时、取消、失败注入和资源耗尽。
- 安全关键解析器、协议、状态机和数值算法增加属性测试（hypothesis）或模糊测试（atheris）。
- 不为了易测而暴露内部实现；通过公共契约、受控依赖注入（mock/patch）和窄适配层建立测试点。

## 测试结构与命名

- 测试文件与被测模块对应，测试类/函数命名表达类型或场景。
- 测试遵循准备、执行、验证（AAA）的清晰结构，一项测试聚焦一个行为，但允许验证该行为的完整结果。
- 优先验证对外行为和不变量，避免对私有调用次数、内部容器顺序等非契约细节过度耦合。
- 断言信息包含必要上下文；浮点、时间和并发结果使用领域允许的容差与不变量，不进行脆弱的精确比较。
- 使用 `@pytest.mark.parametrize` 进行参数化测试，覆盖多组输入。
- 使用 `pytest.raises`/`pytest.warns` 验证预期异常和警告，不捕获后手动断言。

## 确定性与隔离

- 测试不访问在线资源、公共服务、CDN 或开发者个人环境；依赖数据、证书和工具在仓库、测试包或受控离线环境提供。
- 文件测试使用 `tmp_path`/`tmp_path_factory` 生成独立临时目录，结束时清理，不写固定全局路径和用户主目录。
- 不依赖测试执行顺序、共享可变全局状态、真实墙上时间和随机调度。
- 随机测试记录种子；失败时输出可复现种子和最小化输入（hypothesis 自动保存失败用例）。
- 等待异步事件使用 `asyncio.Event`/`queue.Queue`/`asyncio.wait_for` 或可控时钟，不用任意 `asyncio.sleep` 作为同步手段。
- 每项可能阻塞的测试设置合理超时；`pytest-timeout` 超时后保留线程、栈或队列状态等诊断。
- 使用 `monkeypatch`/`unittest.mock.patch` 替换外部依赖，不依赖全局可变状态。

## 静态分析与类型检查

- 项目自有目标启用严格 mypy（`--strict`）并视为错误；第三方目标通过 `exclude` 或 `ignore_errors` 隔离，不全局降低检查等级。
- ruff 配置纳入版本控制，至少覆盖错误易发规则（E/F）、现代化（UP）、安全和性能类别，再根据误报逐条调整。
- `ruff format` 结果在 CI 校验，不依赖开发者手工记忆格式规范。
- mypy/ruff 发现的问题要修复、精确抑制（`# type: ignore[error-code]`）或形成有期限的技术债；禁止批量用 `# type: ignore` 掩盖。
- 类型存根（`.pyi`）与实现同步；第三方无存根的包评估是否需要 `py.typed` 标记或自定义 stub。
- `pyright`/`pyre` 可作为补充类型检查器，但不替代 mypy 作为主检查工具。

## 覆盖率与模糊测试

- 覆盖率按模块和变更风险观察，重点审查新增分支、错误路径和关键算法，而非追求全仓统一数字。
- 生成代码、第三方代码和不可执行声明从覆盖率统计中排除，但不得借此排除项目自有难测逻辑。
- 解析器、反序列化、文件格式、协议入口和复杂状态机优先建立模糊测试（atheris）。
- 模糊测试设置单输入大小、递归深度、运行时间和内存限制；崩溃样本去敏后纳入回归语料库。
- 使用 `coverage.py`/`pytest-cov` 收集覆盖率，结果作为质量门禁参考而非唯一标准。
- 分支覆盖率（`--branch`）优于行覆盖率，覆盖条件分支缺口。

## CI 质量门禁

- 快速门禁：依赖安装、ruff format --check、ruff check、mypy、单元测试。
- 深度门禁：覆盖率、模糊测试种子、组件与集成测试、多 Python 版本矩阵。
- 发布门禁：构建 wheel/sdist、安装、消费方导入、包内容、许可证和核心流程冒烟。
- 支持多 Python 版本或多平台时，至少保留一个主版本快速门禁和受支持矩阵的定期或合并前验证。
- 不允许仅在本地 IDE 中才能运行的测试；所有测试有可脚本化、可重复的 `pytest` 入口。

## 审查清单

- 新行为的成功、失败、边界、取消和资源路径是否都有验证？
- 测试能否离线、并行、乱序和重复运行？
- mypy、ruff 和静态分析是否覆盖项目自有代码？
- 是否从真实发布产物验证了包、插件或可执行程序？
- 覆盖率缺口是否集中在高风险逻辑，是否需要属性或模糊测试？
