# 基于存量 SDK 的二次开发

## 适用范围

本规范适用于依赖存量、专有或第三方 C++ SDK 进行插件、扩展模块、二次开发和系统集成的项目。它约束使用方如何隔离并验证 SDK，不规定 SDK 提供方的产品治理、插件市场或业务功能。

## 企业默认结论

- 通用规范是默认基线；只有经过验证并写入兼容性档案的 SDK 约束可以覆盖默认值。
- 例外只能存在于 SDK 适配目标、包装头文件和边界转换代码中，不得成为整个仓库继续使用旧编码、旧工具链或全局宏的理由。
- 新业务与算法代码不直接依赖 SDK 类型、宏、内存管理、错误码和文本编码；通过自有窄接口访问适配层。
- 不修改供应方 SDK 头文件和二进制。确需补丁时，保留原始版本、补丁、原因、适用版本和可重放步骤。
- “能够编译”不等于兼容；工具链、ABI、编码、所有权、线程和卸载行为都必须有测试证据。

## SDK 兼容性档案

每个受支持的 SDK 版本至少记录：

| 类别 | 必须明确的内容 |
| --- | --- |
| 身份 | SDK 名称、版本、补丁、来源和校验信息 |
| 平台 | 操作系统、架构、最低系统版本、Debug/Release |
| 工具链 | 编译器与工具集、C++ 标准、标准库、C/C++ 运行库、基础框架版本 |
| ABI | 异常、RTTI、调用约定、结构体对齐、导出宏、关键 ABI 宏 |
| 编码 | SDK 头文件源编码、编译器源编码、窄字符执行编码、SDK 字符串/路径/配置/文件/协议编码 |
| 资源 | 对象、缓冲区和句柄由谁创建、复制、释放，释放接口来自哪个模块 |
| 并发 | 回调线程、重入性、同步要求、注册与注销、卸载时在途调用 |
| 部署 | 库搜索方式、依赖布局、配置与资源位置、禁止的环境假设 |

档案中的结论必须来自 SDK 文档、最小探针、真实样本或发布包验证。无法确认的项目标记为“未知风险”，不得默认为兼容。

## 编码决策

编码问题必须拆成三个问题分别回答：

1. 编译器如何读取源文件字节。
2. 普通窄字符串字面量最终产生什么字节。
3. SDK 的 `char*`、配置、路径、文件和协议分别期待什么编码。

按以下规则处理新文件：

| 新文件内容与用途 | 默认处理 |
| --- | --- |
| 只有 ASCII 的源码 | 使用 UTF-8，可安全参与大多数旧工具链构建 |
| 仅注释含非 ASCII | 使用 UTF-8，但必须确认编译器能确定性读取；注释不证明运行时编码正确 |
| 普通字符串字面量含非 ASCII，且不进入 SDK | 遵循本目标已显式定义的执行编码契约 |
| 文本将进入编码非 UTF-8 或不明确的 SDK | 内部保持 Unicode/UTF-8，在适配层显式转换后传入；禁止直接传普通或 `u8` 字面量 |
| SDK 头文件或旧编译器不能在同一目标中可靠处理 UTF-8 | 仅 SDK 适配目标或必要文件采用档案规定的兼容编码，并登记例外与移除条件 |

- 禁止依赖 IDE 显示正常、当前系统区域设置或默认代码页判断编码正确。
- UTF-8 BOM 只能帮助部分工具识别源文件编码，不能决定普通字符串字面量的运行时字节。
- Windows 宽字符、Qt 字符串、SDK 自有字符串与 `std::string` 之间的转换必须命名清晰、集中实现，并显式报告非法输入和不可表示字符。
- 不使用“先转 ASCII”处理中文，不静默替换字符，不按字节截断多字节文本。
- 编码转换或全仓迁移必须单独提交，先建立字节级或往返测试；不得与功能修改、格式化和 SDK 升级混在同一变更中。

## 适配层边界

推荐依赖方向：

    业务/算法目标 -> 自有接口与数据结构 -> SDK 适配目标 -> SDK

- SDK 类型、宏、头文件和库路径只在适配层可见；公共业务接口不暴露 SDK 字符串、容器、智能指针和平台类型。
- 适配层负责文本与路径转换、错误翻译、资源释放、线程切换、版本与能力探测。
- 对不能跨 ABI 边界安全传递的 STL、异常、RTTI 对象、虚类和分配器，使用 SDK 明确支持的接口或自有稳定数据结构。
- SDK 回调进入项目代码时先捕获全部异常，再转换为稳定错误；禁止异常穿过 SDK 或插件边界。

## 构建隔离

- 用 imported target 表示 SDK 二进制和使用要求，用独立 adapter target 承载兼容代码。
- SDK 的 include、link、definition、语言标准、字符集、运行库、警告例外和平台选项按 target 设置，禁止全局 `include_directories`、`link_directories`、`add_definitions` 或全局关闭警告。
- SDK 只能使用较低 C++ 标准时，只降低适配目标；不得因此降低核心业务和算法目标。
- SDK 头文件产生警告时使用 SYSTEM include 或精确豁免，不把项目自有代码的警告门禁一并关闭。
- SDK 路径由 CMake preset、toolchain、缓存变量或受控环境提供；构建失败时明确报告缺失版本或架构，不在脚本中猜测目录。

## 资源、线程与生命周期

- 对 SDK 返回的裸指针、句柄和缓冲区建立 RAII 包装，删除器调用 SDK 指定的释放函数。
- 不跨模块混用 `new/delete`、`malloc/free` 或不同运行库的分配器；对象由哪个模块创建，就由该模块提供的接口销毁。
- 回调保存调用方对象前，必须明确 SDK 是否复制用户数据、何时停止回调以及注销后是否仍可能在途。
- 插件卸载前停止新调用、注销回调、等待在途任务并释放 SDK 资源；禁止依赖进程退出回收。
- 未文档化线程安全的 SDK 默认按非线程安全处理，通过串行化或专用执行器隔离，直至测试和文档证明可并发。

## 最小兼容测试

每个正式支持的兼容组合至少覆盖：

1. 最小源文件独立包含 SDK 公共头并完成编译。
2. 链接或动态加载正确架构和版本的二进制。
3. 创建、调用、失败和释放路径在同一分配契约中闭合。
4. 中文与特殊字符在字面量、参数、返回值、界面、日志、配置和文件路径中按契约往返。
5. 回调线程、重入、注销、取消和插件卸载行为可重复验证。
6. Debug/Release、受支持平台、架构和编译器组合按兼容矩阵运行冒烟测试。

不能自动化的验证要记录环境、输入、期望结果和证据位置，并列为发布门禁；不得只写“人工验证正常”。

## 存量迁移策略

- 先冻结并记录现状，再增加适配层和兼容测试，最后逐步收缩全局宏、全局路径和编码例外。
- 不因现代化目标批量格式化、重命名或转码 SDK 相关存量文件；这些操作会掩盖真实语义变化并扩大回归面。
- 新功能优先写在现代基线目标中；只有必须调用 SDK 的最小代码进入适配目标。
- 每项例外记录原因、适用 SDK/工具链、影响范围、验证方式、负责人和移除条件。

## 审查清单

- 是否建立了可验证的 SDK 兼容性档案，而不是依赖个人经验或 IDE 配置？
- 新文件的源编码、窄字符执行编码和 SDK 数据编码是否分别明确？
- UTF-8、旧编码、低语言标准和警告豁免是否只存在于必要 target 或文件？
- SDK 类型、宏、错误码、资源释放和线程模型是否被限制在适配层？
- 是否验证了真实发布组合中的编译、链接、加载、中文、路径、配置、回调和卸载？
- 例外是否有证据、范围与移除条件，是否避免扩散到新业务代码？
