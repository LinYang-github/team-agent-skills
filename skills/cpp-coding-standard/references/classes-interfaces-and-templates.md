# 类、接口与模板

## 企业默认结论

- 优先使用值语义、组合和普通具体类型；只有确有运行时多态需求时才引入继承体系。
- 类必须维护明确的不变量；构造完成后对象即处于可用状态，不保留“半初始化”对象。
- 默认遵循 Rule of Zero；只有直接管理资源或需要特殊复制、移动语义时才显式声明特殊成员函数。
- 公共接口保持最小、稳定并表达契约；实现细节、缓存和可变状态不得泄露。
- 模板应通过 C++20 concepts 或清晰的约束限定适用类型，不依赖晦涩的替换失败作为日常接口说明。

## 类与数据结构

- 仅承载公开数据且没有不变量的被动聚合可使用 struct；需要封装、不变量或行为的类型使用 class。
- 成员变量默认私有。除被动聚合外，不公开可变数据成员。
- 构造函数完成所有必要校验与初始化；可能失败且失败原因需要返回时，使用命名工厂。
- 单参数构造函数和转换运算符默认声明 explicit，除非该隐式转换具有无歧义、低成本且稳定的领域语义。
- 按声明顺序初始化成员，初始化列表顺序与成员声明顺序保持一致。
- 不使用 init、reset 后才能使用的隐式两阶段初始化；确有状态机语义时，应将状态显式建模并限制非法转换。
- getter 不应无条件暴露内部容器的可变引用；优先返回值、只读引用、span 或受控操作。
- const 成员函数不得通过隐藏的可变状态制造调用者不可见的业务副作用。缓存等技术性变化应受同步和生命周期规则约束。

## 特殊成员与值语义

- 默认让标准容器和 RAII 成员管理资源，使编译器生成析构、复制和移动操作。
- 一旦显式声明析构、复制或移动操作，应审查全部五个特殊成员，并明确复制、移动和禁用策略。
- 不可复制类型显式删除复制构造和复制赋值；不要依赖某个成员“碰巧不可复制”。
- 移动构造和移动赋值仅在确实不会失败时声明 noexcept；这会影响标准容器是否采用移动路径。
- 自定义交换操作应保持 noexcept，并与类型的不变量和资源所有权一致。
- 禁止通过 memcpy、memset 复制或初始化非平凡对象。

## 继承与运行时多态

- 公有继承只表达 is-a 关系；代码复用优先使用组合、委托或自由函数。
- 作为多态基类使用的类型必须具有 public virtual 析构函数；不允许经基类销毁的基类可将析构函数设为 protected 且非 virtual。
- 重写虚函数必须写 override；final 只用于明确封闭扩展点，不作为普遍默认。
- 构造和析构期间不依赖虚函数分派完成业务逻辑。
- 避免深继承树、多重实现继承和脆弱基类。多重继承原则上仅用于纯抽象接口组合。
- 基类不向派生类暴露可变内部状态；需要扩展时提供最小的 protected 操作或组合对象。
- 动态类型转换应是边界性操作。频繁 dynamic_cast 通常说明模型或接口拆分不清晰，应优先重构。

## 公共接口设计

- 参数和返回值应表达所有权、可空性、单位、范围、线程安全和失败方式。
- 小型可复制类型按值传递；只读大对象使用 const 引用；连续非拥有数据使用 span；可空非拥有对象使用指针。
- 返回值优先于输出参数。多结果使用具名结构体，避免调用点难以理解的元组。
- 不使用 bool 参数切换多个行为；使用 enum class、选项结构体或拆分函数。
- 参数较多或容易错位时使用具名 options 结构体，并为字段提供安全默认值。
- 使用 enum class 代替无作用域枚举；使用领域强类型区分单位、标识符和语义不同但底层类型相同的值。
- optional 表达“可能没有值”，variant 表达封闭的互斥状态；不得用特殊整数、空字符串或魔法值代替类型语义。
- 接口不返回指向临时对象、局部对象或内部易失效存储的引用、指针和视图。

## 命名空间与可见性

- 所有库代码置于项目命名空间，避免全局命名空间污染。
- 头文件中禁止 using namespace；实现文件也仅允许在最小局部作用域使用 using 声明。
- 内部实现放入 detail 命名空间、匿名命名空间或私有源文件，但 detail 不视为稳定公共 API。
- 自由函数、辅助类型和常量尽量限制到最小链接和可见范围。
- 同一命名空间内的类、结构体、枚举、函数、类型别名和常量等不得重名；宏虽然不受命名空间约束，也必须在项目内避免与这些名称冲突。

## 模板与泛型

- 模板用于表达真实的类型族、编译期策略或零成本抽象，不为减少少量重复而无边界泛化。
- 对外模板接口优先使用 concepts 和 requires 表达能力要求，并为失败提供可理解的诊断。
- 模板参数命名表达角色，如 Element、Policy、Allocator；单字母名称仅用于局部、惯用且显而易见的数学或迭代语境。
- 模板定义通常与声明一同位于头文件；需要控制编译时间或稳定二进制边界时，可使用显式实例化并记录支持类型集合。
- 依赖基类成员必须按语言规则使用 this->；依赖类型和模板分别使用 typename 与 template 消除歧义。这是 C++ 两阶段查找要求，不应描述为某一操作系统特性。
- 模板实现不得假定具体容器、分配器、字符编码或异常模型，除非约束和文档明确规定。
- 元编程优先使用标准库设施和 concepts；避免难以诊断的递归模板技巧。

## 编译隔离与稳定边界

- 公共头文件减少不必要依赖，能前置声明时审慎前置声明，但不得破坏完整类型需求或可读性。
- PImpl 可用于稳定 ABI、隐藏重型依赖和降低重编译范围；不要为所有小型内部类机械使用。
- 跨编译器、插件或长期稳定 ABI 边界优先使用 C ABI 加不透明句柄，不直接暴露模板和 STL 类型。
- 修改公共类成员、虚函数顺序、基类、对齐或模板参数时，必须评估源码兼容与二进制兼容影响。

## 审查清单

- 对象构造后是否始终有效，非法状态能否被类型系统排除？
- 所有权、可空性、生命周期和失败方式是否能从接口读出？
- 是否可以用值语义或组合替代共享所有权与继承？
- 模板约束和编译错误是否对调用者可理解？
- 公共类型变化是否评估了 API、ABI 与重编译影响？
