# 可移植性与工具链

## 企业默认结论

- 新项目默认使用 C++20；采用 C++23 特性前，必须验证全部目标编译器、标准库、分析工具和部署平台。
- 项目维护明确的支持矩阵：操作系统、架构、编译器、标准库、运行库、构建类型和最低版本。
- 构建以命令行 CMake 和 CMakePresets 为事实来源，IDE 只消费同一配置，不拥有独立隐式设置。
- 自有且可控的源码、配置和文本资源默认 UTF-8；受存量 SDK 约束的适配目标可以采用已验证的兼容编码，但必须记录范围并阻止该例外扩散。
- 平台差异集中在适配层、工具链文件和平台源文件，不让条件编译散布业务代码。
- 发布必须验证目标架构、动态依赖、符号、安装布局和离线运行，不以“编译成功”替代可交付性。

## 支持矩阵

- README 或工程文档列出受支持与仅开发验证的平台，避免把“理论可编译”当正式支持。
- 每个正式平台至少保留一种受支持编译器配置；关键库应在两种主流编译器族上验证以发现非标准依赖。
- 明确 x86_64、AArch64 等架构，不用模糊的 64 位替代架构和 ABI 描述。
- 编译器、标准库和第三方依赖版本统一由预设、工具链或锁定清单管理，不写在个人 IDE 配置中。
- 升级工具链作为独立变更执行完整构建、测试、Sanitizer、ABI 和发布包验证。

## 编译器基线与警告

- GCC 和 Clang 项目自有代码至少启用 Wall、Wextra、Wpedantic 等同等级警告；MSVC 至少启用 W4、permissive-、utf-8 和正确的标准版本宏。
- 更严格警告如 conversion、sign-conversion 和 shadow 根据代码库成熟度逐项启用；不得一次开启后用大范围抑制抵消。
- 项目自有代码警告视为错误；第三方与生成代码通过目标边界隔离。
- 不全局关闭某条警告。例外应缩小到具体目标、文件或表达式，并解释工具链版本、风险和移除条件。
- 编译选项通过目标配置和生成器表达式按编译器设置，不把某编译器参数直接传给全部平台。

## 工具版本与统一入口

- clang-format、clang-tidy、CMake、测试框架和代码生成器记录支持版本或版本范围。
- 格式化、静态分析、测试、Sanitizer 和打包提供统一脚本或 CMake 目标，开发机与 CI 使用同一入口。
- 编译命令数据库由构建系统产生，供 IDE 和分析工具消费。
- 禁止依赖仅存在于某位开发者 shell、IDE 插件或用户主目录的隐藏设置。

## 路径、文件名与头文件

- include 路径统一使用正斜杠，并严格匹配磁盘文件名大小写；持续集成至少包含大小写敏感文件系统验证。
- 不在源码中硬编码盘符、用户目录、安装绝对路径和构建机目录。
- 使用 std::filesystem::path 组合路径、查询属性和遍历目录，不用字符串替换模拟路径语义。
- 路径与文本之间的转换集中在平台边界；Windows 原生宽字符接口由适配层处理，业务层保持 UTF-8 契约。
- 不使用跨目录的多层相对 include；通过目标 include 目录和稳定公共前缀建立依赖。
- 路径作为数据时，均使用 “正斜杠” 分隔符。

## 字符编码与文本

- 分别定义并记录三种编码，禁止用一句“项目使用 UTF-8”代替：源文件编码、编译器窄字符执行编码，以及 SDK/文件/配置/路径/协议的数据编码。
- 自有 C++ 源码、CMake、配置、脚本和可控文本文件默认采用 UTF-8；是否带 BOM 由仓库统一，不混用。只有工具链或 SDK 头文件确实要求其他编码时，相关适配目标或文件才可例外。
- 编译器必须显式或可重复地识别源文件编码；BOM 只影响部分工具链对源文件的识别，不能保证普通字符串字面量在运行时采用 UTF-8。
- 非 ASCII 普通字符串字面量不得直接传给编码契约不明或要求本地代码页、GBK/GB18030 等编码的 SDK。`u8` 字面量产生 UTF-8 数据，也不能直接代替边界转换。
- 内部文本优先采用 Unicode/UTF-8 契约；进入或离开 SDK、系统 API 和旧文件格式时，在适配层显式转换并处理失败。
- 不批量转换第三方 SDK、生成代码或尚未建立兼容测试的存量文件。编码迁移作为独立变更执行，并验证编译、链接、界面文本、文件路径、配置读写和数据往返。
- 对外文件和协议显式声明编码，读取时校验；不依赖系统区域设置和当前代码页。
- Windows 本地 API 的 UTF-16 与内部 UTF-8 在适配层显式转换，转换失败必须可观察。
- 不以 ASCII 中转中文文本，不按字节截断 UTF-8 字符串，不把字符数与字节数混为一谈。
- 面向二进制数据使用 byte、span 或显式缓冲区类型，不借用字符串承载任意字节。

## 平台抽象

- 不在公共领域接口暴露 DWORD、TCHAR、HANDLE 等平台类型；平台类型只存在于适配实现。
- 不为兼容平台而在全局重新定义系统类型和宏。
- 条件编译优先选择平台源文件和窄适配层；单个函数内大量 ifdef 通常应拆分实现。
- 使用标准库能力代替平台 API 时，先核实语义、错误行为和性能满足要求。
- 对字节序、对齐、打包、整数宽度和符号性不作隐式假设；序列化使用明确格式。

## 交叉编译与架构

- 交叉编译参数集中在 CMake toolchain 文件和 preset 中，包含编译器、sysroot、目标架构和查找策略。
- 构建主机工具与目标产物分离，代码生成器不得误用目标架构可执行文件。
- 各架构依赖放入可识别的包和目录，不靠运行脚本临时猜测库路径。
- SIMD 和专用指令集通过编译期目标或运行时能力检测启用，并提供符合支持矩阵的回退路径。
- 不从 sizeof(long)、指针大小或预定义平台宏推断完整 ABI；使用固定宽度类型和明确能力检查。

## 动态库与运行时依赖

- 发布前检查动态库架构、导出符号、未解析符号、运行库版本和依赖搜索路径。
- Linux 可使用 file、readelf、objdump 和受控环境下的 ldd -r；macOS 使用 file、otool 和 nm；Windows 使用 dumpbin 或等价离线工具。
- 不对不可信二进制直接执行可能加载代码的依赖检查工具；先使用静态检查手段。
- 运行时搜索路径通过安装布局、RPATH/RUNPATH、加载器配置或受控启动脚本解决；LD_LIBRARY_PATH 仅用于诊断或封闭部署脚本。
- 禁止通过修改用户的 shell 启动文件修复应用依赖，部署不得污染个人环境。
- 明确哪些系统库由目标系统提供，哪些依赖随产品交付，并检查许可证和安全更新策略。

## 安装、打包与发布

- install 规则定义运行时、库、公共头文件、配置模板、资源、许可证和调试符号的目标位置。
- 发布包不包含源码树绝对路径、临时文件、测试密钥、开发配置和无关依赖。
- 可执行程序提供版本、构建标识、目标架构和必要特性信息，便于现场诊断。
- 每个平台从空目录安装并运行消费测试，验证包内查找关系而非构建树偶然路径。
- 调试符号按交付策略分离并可与构建标识关联；Release 构建不能完全失去崩溃定位能力。
- 可复现构建控制时间戳、文件顺序、生成器输入和环境依赖；无法完全复现时记录剩余差异来源。

## 审查清单

- 支持矩阵是否明确到编译器、标准库、架构和构建模式？
- 新代码是否依赖大小写不敏感路径、系统代码页或个人环境？
- 源文件编码、编译器执行编码和 SDK 数据编码是否被分别定义并验证？
- 平台条件是否被限制在适配层和构建配置？
- 发布包的架构、动态依赖、搜索路径和离线运行是否经过验证？
- 工具链升级和新语言特性是否覆盖全部目标环境？
