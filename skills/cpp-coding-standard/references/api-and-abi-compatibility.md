# API 与 ABI 兼容

## 企业默认结论

- 先明确交付的是源码接口、同工具链二进制接口，还是跨编译器、跨语言、长期稳定的二进制接口；三者不能共用模糊承诺。
- 仅供同仓库构建的模块优先提供类型安全的 C++ API；跨编译器、插件或长期稳定边界默认采用 C ABI、不透明句柄和版本化数据结构。
- 公共 API 必须说明所有权、生命周期、可空性、线程安全、错误模型、单位、编码和兼容策略。
- 动态库默认隐藏符号，仅显式导出承诺的公共入口。
- 异常、STL 容器、模板实例、RTTI 对象和编译器特有类型不得跨越不受控 ABI 边界。

## 区分 API 与 ABI

- API 兼容指已有调用方源码无需修改或只需重新编译即可继续工作。
- ABI 兼容指已有二进制无需重新编译即可加载、链接并保持行为。
- 修改名称、签名、默认行为、异常保证和语义可能破坏 API。
- 修改对象大小、成员顺序、对齐、虚函数表、基类、内联实现、模板参数或调用约定可能破坏 ABI。
- 评审公共变更时必须分别给出 API 和 ABI 影响，不用“向后兼容”笼统代替。

## 公共 C++ API

- 公共头文件自包含、依赖最小，不暴露内部目录、私有宏和非必要第三方类型。
- 参数与返回类型表达所有权和缺省语义；不得要求调用方猜测释放函数或有效期。
- 公共枚举保留未知值处理策略；新增枚举值时，调用方不应因穷尽假设进入未定义行为。
- 接口的线程安全级别明确为线程兼容、实例可并发、只读可并发或完全线程安全。
- 不轻易在公共接口中暴露具体容器、分配器、时钟和执行器；确需暴露时，将其视为长期契约。
- 公共内联函数和模板的实现变化会传播到调用方二进制，应纳入版本和重编译策略。

## 稳定 C ABI

- 使用 extern C 导出稳定入口，采用固定宽度整数、字节缓冲区、长度和不透明句柄。
- 结构体携带 size 和 version 字段；新增字段只追加到末尾，读取前检查调用方提供的结构大小。
- 明确字符串编码、是否包含终止符、缓冲区容量、实际写入长度和截断行为。
- 内存由分配方释放。跨运行库返回动态内存时，必须提供同模块释放函数，或由调用方提供缓冲区与分配回调。
- 不在边界传递 std::string、std::vector、std::function、异常、虚类、type_info 和编译器特有布局类型。
- 导出函数捕获全部异常，返回稳定状态码；诊断信息通过显式错误查询或调用方缓冲区获取。
- 回调接口说明调用线程、是否可重入、调用时机、用户上下文生命周期和注销后的在途回调行为。

## 符号与动态库

- GCC/Clang 使用隐藏默认可见性，MSVC 使用显式导出/导入宏；公共宏集中定义并覆盖静态链接场景。
- 只导出承诺的入口，不依赖链接器偶然暴露内部符号。
- 对外发布时生成并检查导出符号清单；新增、删除或签名变化进入兼容性审查。
- 不依赖静态对象跨动态库的初始化顺序；插件注册通过显式入口完成。
- 同一对象的创建、使用和销毁不得跨越不兼容 C++ 运行库或分配器边界。

## C++ ABI 稳定手段

- 若必须提供 C++ ABI，固定支持的编译器、标准库、运行库、编译选项、架构和构建模式，并写入兼容矩阵。
- 使用既有 SDK 前建立兼容性档案，至少锁定 SDK 版本、编译器与工具集、标准库/运行库、Qt 等基础库、架构、Debug/Release、异常/RTTI、调用约定、结构体对齐、导出宏和关键 ABI 宏；不能只凭头文件可编译判定兼容。
- 使用 PImpl 隔离私有成员布局和重型依赖；PImpl 不能掩盖虚函数、基类和公共内联代码的 ABI 变化。
- 公共多态接口保持纯粹、最小，避免数据成员和模板方法；新增虚函数通常会破坏既有布局与实现。
- 不将 Debug 与 Release、不同运行库、不同异常或 RTTI 配置的二进制视为天然兼容。
- 编译器升级、标准库升级和构建选项变化必须执行 ABI 检查与实际加载测试。

## 数据与协议兼容

- 不通过原始内存拷贝、结构体落盘或直接发送对象布局建立持久化和网络协议。
- 协议明确字节序、字段宽度、编码、对齐、版本、缺省值、未知字段和最大长度。
- 解析所有外部数据时执行长度、范围、数量、递归深度和资源预算校验。
- 版本升级优先采用可忽略新增字段的扩展方式；字段删除、改义和复用编号属于破坏性变更。

## 版本、弃用与插件握手

- 公共接口采用一致版本策略，区分兼容新增、行为修正和破坏性变更。
- 弃用必须提供替代方案、迁移说明和移除版本；不能只加 deprecated 标记后无限保留。
- 插件加载首先完成 ABI 版本、结构大小、能力集和必要运行时条件握手，不直接假定兼容。
- 不兼容时返回清晰错误并拒绝加载，不尝试带病运行。

## 验证要求

- 公共头文件在最小调用方工程中独立编译。
- 动态库执行导出符号快照、ABI 差异检查、跨版本加载和创建/销毁冒烟测试。
- 发布包至少在每个受支持平台和架构执行安装后消费测试，而不只验证源码树内构建。
- 兼容性测试保存上一受支持版本的头文件、二进制或协议样本作为基线。

## 审查清单

- 当前边界需要源码兼容、同工具链 ABI，还是跨工具链稳定 ABI？
- 谁创建和销毁对象，字符串、缓冲区和回调能存活多久？
- 是否泄露了 STL、异常、RTTI、分配器或第三方实现细节？
- 此变更是否影响布局、符号、虚表、内联实现、协议字段或运行库？
- 是否有旧版本消费方和真实发布包的兼容性验证？
