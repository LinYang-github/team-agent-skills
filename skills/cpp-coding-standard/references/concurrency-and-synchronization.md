# 并发与同步

## 企业默认结论

- 并发设计必须明确任务所有者、数据所有者、取消方式、超时、背压和关闭顺序。
- C++20 项目优先使用 std::jthread 与 stop_token 管理可协作取消的线程；线程对象不得无主存活。
- 禁止把 detach 作为规避 join 的手段。仅进程级基础设施且生命周期被严格证明时允许例外，并记录退出行为。
- 优先使用不可变数据、消息传递、任务队列和所有权转移；共享可变状态是受控例外。
- 工作队列、线程池、缓存和生产消费通道必须有界，并定义满载策略。
- 原子操作默认使用顺序一致内存序；采用更弱内存序必须附并发协议、正确性说明和基准证据。

## 线程与任务生命周期

- 创建线程或提交异步任务的组件负责停止、等待和回收，不把生命周期责任隐式转交给调用者。
- 不直接散布 std::thread；通过拥有型组件、执行器或线程池集中管理名称、数量、优先级、异常和关闭。
- 线程入口设置必要的名称和上下文，并建立异常屏障；任何异常都不能逃逸线程函数。
- 捕获到异步任务中的对象必须保证任务完成前有效；优先按值捕获不可变数据或转移所有权。
- 禁止无保护地捕获 this 后让任务超越对象生命周期。使用受控所有权、weak_ptr 检查、取消后等待，或把任务状态与对象分离。
- std::async 仅在启动策略和 future 生命周期明确时使用，不依赖实现选择的延迟或并发语义。

## 有界执行与背压

- 线程数量根据 CPU、阻塞特性和资源预算设定，不按请求、连接或数据项无限创建线程。
- 队列必须配置容量，并明确队满时阻塞、超时、拒绝、丢弃旧项、合并还是降级。
- 提交接口返回可观察结果，不能静默丢任务。
- 生产者速度可能超过消费者时，在设计阶段建立背压；不得依赖内存耗尽作为限流机制。
- 任务应具有合理粒度，避免过细调度成本或单个任务长期独占工作线程。

## 锁与临界区

- 使用 lock_guard、unique_lock 或 scoped_lock 管理锁，禁止手工 lock 与 unlock 分散在控制流中。
- 临界区只包含保护共享状态所需的最小操作；锁内不执行不受控 I/O、阻塞等待、外部回调或用户代码。
- 多把锁建立全局锁顺序；需要同时获取多把锁时优先使用 scoped_lock，避免逐把获取导致死锁。
- 锁保护哪些数据必须在声明附近说明。共享状态和对应互斥量尽量封装在同一类型中。
- 不返回受锁保护对象的可变引用或指针，使其在解锁后逃逸。
- 读写锁仅在读占绝对多数且基准证明有收益时使用；不要假定 shared_mutex 必然更快或无饥饿。
- 递归互斥量不是修复重入设计的默认方法，应优先消除隐式递归调用。

## 条件变量与等待

- 条件变量始终与谓词配合使用，并在循环或带谓词重载中检查条件，以处理虚假唤醒。
- 修改受保护状态与检查谓词使用同一互斥协议；通知时机应保证等待方能够观察新状态。
- 所有可能无限等待的操作必须评估超时、取消和关闭唤醒机制。
- 超时和持续时长使用 steady_clock；只有表示日历时间时才使用 system_clock。
- 等待返回后必须区分条件满足、超时、取消和关闭，不把它们折叠为模糊的 false。

## 原子与无锁代码

- atomic 只保证相关原子对象的访问，不自动保护由多个字段组成的不变量。
- 优先使用互斥量表达复合状态；仅在性能数据证明锁是瓶颈且团队能够维护内存模型时采用无锁设计。
- 使用 acquire/release、relaxed 或栅栏时，必须在代码附近写明同步关系、参与线程、发布对象和生命周期前提。
- relaxed 只用于不建立跨对象同步的独立计数等场景，不能用于发布指针或对象初始化。
- 无锁算法必须测试 ABA、回收、溢出、伪共享和弱内存架构，并通过专门审查。

## 数据发布与共享

- 对象在发布给其他线程前必须完成初始化，并通过锁、原子发布、队列或其他明确 happens-before 关系传递。
- 优先发布不可变快照；更新通过构造新值后原子替换或受锁交换完成。
- 不并发访问普通容器，即使不同线程看似操作不同元素，除非标准保证且容器结构不会变化。
- 缓存、单例和延迟初始化使用函数局部静态初始化或 call_once，不手写双重检查锁定。
- 避免 false sharing；高频独立计数需要基准和布局检查后再使用对齐隔离。

## 取消与关闭

- 取消是协作协议。长循环、阻塞点和批处理边界定期检查停止请求。
- 关闭过程明确状态机：停止接收、请求取消、唤醒等待、排空或丢弃、等待完成、释放资源。
- close、stop 和 shutdown 应尽可能幂等，并允许从预期控制线程安全调用。
- 不在持锁状态 join 可能反向获取该锁的线程；关闭顺序要消除循环等待。
- 超时退出后不得遗留仍访问已销毁状态的后台任务。

## 验证要求

- 并发单元测试覆盖启动、正常完成、取消、超时、队满、关闭竞争和异常路径。
- 使用屏障、锁存器或可控执行器协调测试，不用任意 sleep 猜测调度时机。
- ThreadSanitizer 使用独立流水线运行，不与 AddressSanitizer 合并为同一进程配置。
- 对锁竞争、队列深度、任务延迟和拒绝量建立可观测指标，但不得输出敏感业务数据。
- 压力测试和长稳测试不能替代内存模型与生命周期审查。

## 审查清单

- 谁拥有线程、任务和共享数据，何时结束？
- 队列和线程数是否有界，满载时会发生什么？
- 是否在持锁时调用外部代码、等待或执行 I/O？
- 是否存在对象先销毁、回调后到达或取消后仍运行的路径？
- 每个原子内存序和无锁假设是否有明确证明与测试？
