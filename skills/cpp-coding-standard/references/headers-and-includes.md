# 头文件与包含规范

## 默认防重复包含

所有项目内手工维护、且编译器支持矩阵限定为主流 MSVC/GCC/Clang 的 C/C++ 头文件默认只使用：

    #pragma once

- 放在版权声明之后、其他预处理指令之前。
- 同一头文件不得同时使用 #pragma once 和宏式 include guard。
- 不依赖 IDE 或插件生成功能；CI 应检查新增和修改的头文件。

只有以下场景使用宏式 include guard：

- 对外 SDK 需要支持未纳入企业基线的预处理器。
- 严格 ISO 可移植性、特殊嵌入式或遗留编译器明确要求。
- 代码生成器或外部接口规范规定宏式保护。

例外宏统一为 ORGANIZATION_PRODUCT_PATH_FILE_H_ 形式，全部大写且在发布范围内唯一；不得以下划线开头，不得使用双下划线，不得依赖 GUID 或个人 IDE 生成规则。例外原因和支持矩阵必须记录。

## 自包含

- 每个头文件必须能作为翻译单元的第一个 include 独立编译。
- 头文件直接包含声明和定义所需依赖，不依赖传递包含、预编译头或包含顺序偶然成立。
- 源文件首先包含与自身对应的头文件，以尽早暴露缺失依赖和接口不一致。
- 能前置声明时只在确实降低稳定依赖且不需要完整类型的场景使用；不要为减少 include 牺牲正确性。
- 使用类型别名、继承、按值成员、sizeof、析构或模板实例化需要完整类型时必须包含定义。

## 包含形式与顺序

默认顺序：

1. 当前源文件对应的头文件。
2. C++ 标准库头文件。
3. 第三方库头文件。
4. 当前项目头文件。

组间保留一个空行，组内由 clang-format 按稳定规则排序。

- 标准库和第三方已安装接口使用尖括号；当前项目头文件使用双引号。
- 包含路径从 target 暴露的 include 根开始，不使用跨目录 ../../。
- 路径统一使用 /，文件名大小写必须与磁盘完全一致。
- C++ 代码优先使用 cstdint、cstdio 等 C++ 包装头，不使用带全局命名污染的旧式 .h 版本，除非对接 C API。

## 头文件内容

- 头文件不使用 using namespace；公共头文件中的 using 声明和类型别名必须控制暴露范围。
- 不在头文件定义非 inline 的全局对象或函数，避免 ODR 冲突。
- C++17 及以上共享编译期常量优先 inline constexpr；不要依赖头文件中的可变全局状态。
- 模板、concept 和必须 inline 的实现可以位于头文件；大段模板实现可放入同名 .ipp/.tpp 并由公共头文件包含。
- 公共头文件尽量不暴露重量级第三方依赖；必要时使用适配接口或 PImpl，但不得以悬空前置声明换取编译速度。
- 条件编译保持局部且成对，复杂平台分支移入独立实现文件。

## 预编译头与生成头

- 预编译头只用于构建性能，不承担正确性；移除预编译头后代码仍应通过直接依赖编译。
- 预编译头不得包含业务配置、可变宏或改变公共接口语义的定义。
- 生成头文件必须有确定输入、输出位置和构建依赖；不得依赖人工先运行 IDE 命令。
- 不手工修改生成头；需要调整时修改生成器、模板或输入。

## 自动验收

- CI 独立编译公共头文件或运行等价的 header self-containment 检查。
- clang-format 检查 include 分组和排序；可按需要使用 include-what-you-use，但修复结果必须人工确认接口和完整类型要求。
- Linux/大小写敏感环境至少执行一次构建，避免大小写不敏感开发环境的问题进入仓库。
