# 可移植性与工具链

## 企业默认结论

- 新项目默认使用 .NET 8 / C# 12；采用更高版本特性前，必须验证全部目标 SDK、运行时、分析器和部署平台。
- 项目维护明确的支持矩阵：操作系统、架构、.NET 运行时、构建类型和最低版本。
- 构建以命令行 `dotnet` 和 .csproj 为事实来源，IDE 只消费同一配置，不拥有独立隐式设置。
- 源码、配置和文本资源默认 UTF-8；路径使用 `System.IO.Path`/`Path.Combine`，跨平台代码不手工拼接分隔符。
- 平台差异集中在适配层、`<RuntimeIdentifier>`/`<OSPlatform>` 和平台源文件，不让条件编译散布业务代码。
- 发布必须验证目标架构、动态依赖、符号、安装布局和离线运行，不以“编译成功”替代可交付性。

## 支持矩阵

- README 或工程文档列出受支持与仅开发验证的平台，避免把“理论可编译”当正式支持。
- 每个正式平台至少保留一种受支持 .NET 运行时配置；关键库应在多目标框架上验证以发现非标准依赖。
- 明确 x64、arm64 等架构，不用模糊的 64 位代替架构和 ABI 描述。
- .NET SDK、运行时和第三方依赖版本统一由 `global.json`、`Directory.Packages.props` 或锁定清单管理，不写在个人 IDE 配置中。
- 升级 SDK/运行时作为独立变更执行完整构建、测试、分析器和发布包验证。

## 编译器基线与警告

- 项目自有代码至少启用 `<TreatWarningsAsErrors>`、`<EnableNETAnalyzers>`、`<AnalysisLevel>` 和正确的 `<LangVersion>`。
- 更严格分析器规则（CA1707、CA2007 等）根据代码库成熟度逐项启用；不得一次开启后用大范围抑制抵消。
- 项目自有代码警告视为错误；第三方与生成代码通过目标边界隔离。
- 不全局关闭某条警告。例外应缩小到具体项目、文件或表达式，并解释 SDK 版本、风险和移除条件。
- 编译选项通过 MSBuild 属性和条件按平台设置，不把某平台参数直接传给全部目标。

## 工具版本与统一入口

- `dotnet format`/csharpier、Roslyn 分析器、xUnit、`dotnet-coverage` 和代码生成器记录支持版本或版本范围。
- `global.json` 锁定 .NET SDK 版本；CI 与开发机使用同一入口。
- 格式化、静态分析、测试、发布提供统一脚本或 `dotnet` 目标，开发机与 CI 使用同一入口。
- 禁止依赖仅存在于某位开发者 shell、IDE 插件或用户主目录的隐藏设置。
- Visual Studio/Rider/VS Code 使用同一 .csproj 与 .editorconfig，不维护 IDE 专用配置。

## 路径、文件名与跨平台

- 路径统一使用 `Path.Combine`/`Path.DirectorySeparatorChar`；持续集成至少包含大小写敏感文件系统验证。
- 不在源码中硬编码盘符、用户目录、安装绝对路径和构建机目录。
- 使用 `System.IO.Path` 组合路径、查询属性和遍历目录，不用字符串替换模拟路径语义。
- 路径与文本之间的转换集中在平台边界；Windows 原生宽字符接口由适配层处理，业务层保持 UTF-8 契约。
- 不使用跨目录的多层相对路径；通过项目引用和稳定公共前缀建立依赖。
- 路径分隔符、换行符、大小写敏感和文件属性差异集中处理，不散落业务代码。

## 字符编码与文本

- C# 源码、.csproj、配置、脚本和可控文本文件采用 UTF-8；是否带 BOM 由仓库统一，不混用。
- 对外文件和协议显式声明编码，读取时校验；不依赖系统区域设置和当前代码页。
- Windows 本地 API 的 UTF-16 与内部 UTF-8 在适配层显式转换，转换失败必须可观察。
- 不以 ASCII 中转中文文本，不按字节截断 UTF-8 字符串，不把字符数与字节数混为一谈。
- 面向二进制数据使用 `byte`/`ReadOnlySpan<byte>`，不借用字符串承载任意字节。
- `CultureInfo` 显式传递（`InvariantCulture`/`CurrentCulture`），不依赖系统区域格式化数字和日期。

## 平台抽象

- 不在公共领域接口暴露 `IntPtr`、`SafeFileHandle`、`Registry` 等平台类型；平台类型只存在于适配实现。
- 不为兼容平台而在全局重新定义系统类型和宏。
- 条件编译优先选择平台源文件和窄适配层；单个方法内大量 `#if` 通常应拆分实现。
- 使用标准库能力代替平台 API 时，先核实语义、错误行为和性能满足要求。
- 对字节序、对齐、整数宽度和符号性不作隐式假设；序列化使用明确格式。
- `[SupportedOSPlatform]`/`[UnsupportedOSPlatform]` 标注跨平台 API，分析器在编译期发现问题。

## 交叉编译与架构

- 交叉编译参数集中在 `dotnet publish -r <RID>` 和 .csproj 属性中，包含目标架构和运行时标识。
- 各架构依赖放入可识别的 NuGet 包和目录，不靠运行脚本临时猜测库路径。
- 运行时标识（RID）使用官方图谱（win-x64、linux-x64、linux-arm64、osx-arm64 等），不自创 RID。
- SIMD 和专用指令集通过 `System.Numerics`/`Vector<T>` 或运行时能力检测启用，并提供符合支持矩阵的回退路径。
- 不从 `IntPtr.Size` 或预定义平台宏推断完整 ABI；使用固定宽度类型和明确能力检查。

## 程序集与运行时依赖

- 发布前检查程序集架构、导出类型、未解析依赖和运行时版本。
- 可使用 `dotnet publish`、`ILSpy`/`ildasm` 和受控环境下的依赖检查。
- 不对不可信二进制直接加载；先使用静态检查手段。
- 运行时搜索路径通过 `deps.json`、`AssemblyLoadContext` 或受控启动脚本解决；`PROBING` 仅用于诊断或封闭部署脚本。
- 禁止通过修改用户的全局环境修复应用依赖，部署不得污染个人环境。
- 明确哪些系统运行时由目标系统提供，哪些依赖随产品交付，并检查许可证和安全更新策略。

## 安装、打包与发布

- `dotnet publish` 规则定义运行时、库、公共 API、配置模板、资源、许可证和调试符号的目标位置。
- 发布包不包含源码树绝对路径、临时文件、测试密钥、开发配置和无关依赖。
- 可执行程序提供版本、构建标识、目标架构和必要特性信息，便于现场诊断。
- 每个平台从空目录安装并运行消费测试，验证包内查找关系而非构建树偶然路径。
- 调试符号（PDB）按交付策略分离并可与构建标识关联；Release 构建不能完全失去崩溃定位能力。
- 可复现构建控制时间戳、文件顺序、生成器输入和环境依赖；无法完全复现时记录剩余差异来源。
- Trimming/AOT 发布验证反射、序列化和动态加载兼容性；不假设全部第三方依赖兼容 Trim/AOT。

## 审查清单

- 支持矩阵是否明确到 SDK、运行时、架构和构建模式？
- 新代码是否依赖大小写不敏感路径、系统区域格式或个人环境？
- 平台条件是否被限制在适配层和构建配置？
- 发布包的架构、运行时依赖、搜索路径和离线运行是否经过验证？
- 工具链升级和新语言特性是否覆盖全部目标环境？
