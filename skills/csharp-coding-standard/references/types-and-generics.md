# 类型、接口与泛型

## 企业默认结论

- 优先使用值语义、组合和普通具体类型；只有确有运行时多态需求时才引入继承体系。
- 类必须维护明确的不变量；构造完成后对象即处于可用状态，不保留“半初始化”对象。
- 公共接口保持最小、稳定并表达契约；实现细节、缓存和可变状态不得泄露。
- 泛型应通过约束限定适用类型，不依赖晦涩的替换失败作为日常接口说明。

## 类与数据结构

- 仅承载公开数据且没有不变量的被动聚合可使用 `struct` 或 `record struct`；需要封装、不变量或行为的类型使用 `class`。
- 成员变量默认私有。除被动聚合外，不公开可变数据成员；需要外部访问的字段增加属性。
- 构造函数完成所有必要校验与初始化；可能失败且失败原因需要返回时，使用命名工厂。
- 按声明顺序初始化成员，初始化器顺序与字段声明顺序保持一致。
- 不使用 `init`/`reset` 后才能使用的隐式两阶段初始化；确有状态机语义时，应将状态显式建模并限制非法转换。
- getter 不应无条件暴露内部集合的可变引用；优先返回值、只读集合、`ImmutableArray<T>` 或受控操作。
- 属性中的代码块尽量简练，否则以方法代替；属性不应产生调用者不可见的复杂副作用。
- 要在类中显式声明公用的默认构造函数。

## 记录与值语义

- `record` 表达值语义的不可变数据；默认基于引用相等，可按需重写为值相等。
- `record struct` 表达值类型的不可变数据；注意 struct 拷贝语义和默认值。
- `record` 的 `with` 表达式用于非破坏性更新；不用于表达有副作用的修改。
- 需要 `IDisposable` 的类型谨慎使用 `record`；值语义与释放语义可能冲突，优先显式释放方法。
- `init` setter 保护不可变契约；公共可变属性使用 `set` 时必须证明可变性必要性。

## 特殊成员与值语义

- `struct` 是值类型，按值传递可能产生拷贝成本；大 struct（>16 字节）考虑使用 `class` 或 `in`/`ref` 参数。
- 不可变 struct 优先 `readonly struct`；可变 struct 易产生隐式拷贝 bug。
- `ref struct` 不可装箱、不可作为字段、不可跨越 `await`；用于栈上临时视图（`Span<T>`）。
- 重写 `Equals`/`GetHashCode` 时必须成对实现并保证一致性；`record` 自动生成。
- 不使用 `null`、特殊整数、空字符串或魔法值代替类型语义。

## 继承与运行时多态

- 公有继承只表达 is-a 关系；代码复用优先使用组合、委托或扩展方法。
- 作为多态基类使用的类型，析构/finalizer 行为需明确；C# 不支持虚析构函数，使用 `IDisposable`。
- 重写方法必须写 `override`；`sealed` 只用于明确封闭扩展点，不作为普遍默认。
- 构造期间不调用虚方法完成业务逻辑，避免派生类未初始化。
- 避免深继承树、脆弱基类；多重继承仅通过接口实现。
- 类型转换应是边界性操作。频繁 `as`/`is`/`cast` 通常说明模型或接口拆分不清晰，应优先重构。
- 不应使用 `C` 前缀为类名加前缀；接口使用 `I` 前缀。

## 公共接口设计

- 参数和返回值应表达所有权、可空性、单位、范围、线程安全和失败方式。
- 小型可复制类型按值传递；只读大对象使用 `in`；连续非拥有数据使用 `ReadOnlySpan<T>`；可空非拥有对象使用可空引用。
- 返回值优先于 `out` 参数。多结果使用具名元组或命名结构体，避免调用点难以理解的元组。
- 不使用 `bool` 参数切换多个行为；使用 `enum`、选项对象或拆分函数。
- 参数较多或容易错位时使用具名 options 对象，并为字段提供安全默认值。
- 使用 `enum` 代替魔法值；使用领域强类型（如 `record struct Id<T>`）区分单位、标识符和语义不同但底层类型相同的值。
- `Nullable<T>`/可空引用表达“可能没有值”；`OneOf`/`Result<T>` 表达封闭的互斥状态。
- 接口不返回指向临时对象、局部对象或内部易失效存储的 `ref`/`Span`。

## 命名空间与可见性

- 所有库代码置于项目命名空间，避免全局命名空间污染。
- 实现细节放入 `internal` 类、`private` 嵌套类型或 `Internal` 命名空间，不视为稳定公共 API。
- 命名空间一般格式：`<Company>.(<Product>|<Technology>)[.<Feature>][.<Subnamespace>]`，如 `Huaru.XAnalyst.TargetMain`。
- 自由函数（静态方法）、辅助类型和常量尽量限制到最小可见范围。
- 程序集和 DLL 名称规则：`<Company>.<Component>.dll`，如 `Contoso.WebControls.dll`。

## 泛型与约束

- 泛型用于表达真实的类型族、编译期策略或零成本抽象，不为减少少量重复而无边界泛化。
- 对外泛型接口优先使用约束表达能力要求，并为失败提供可理解的诊断。
- 泛型参数命名表达角色，如 `TElement`、`TPolicy`、`TKey`；单字母名称仅用于局部、惯用且显而易见的语境。
- 泛型约束（`where`）必须明确：`struct`/`class`/`notnull`/`unmanaged`/`new()`/接口约束，不依赖隐式假设。
- 协变/逆变（`in`/`out`）只在确实表达方向语义时使用，并验证赋值兼容性。
- 泛型方法优先非泛型方法或具体类型，只有真实复用时引入；避免过度泛化。

## 委托、事件与扩展方法

- 委托类型命名使用动词，如 `Action`、`Func`、自定义委托使用 `EventHandler` 后缀。
- 事件使用 `EventHandler<T>` 模式；`sender` 和 `e` 参数无需 XML 注释。
- 事件订阅必须配对取消订阅，长生命周期对象订阅短生命周期对象需在 `Dispose` 中取消。
- 扩展方法只在确实为第三方类型添加领域语义时使用，不滥用扩展方法替代实例方法。
- 扩展方法集中放在静态类，命名空间与扩展类型相关，避免污染全局 `using`。

## 编译隔离与稳定边界

- 公共 API 减少不必要依赖，能使用接口时审慎使用，但不得破坏完整类型需求或可读性。
- 抽象/适配器可用于稳定 API、隐藏重型依赖和降低重编译范围；不要为所有小型内部类机械使用。
- 跨程序集、插件或长期稳定 API 边界优先使用接口加 DTO，不直接暴露内部实现和可序列化内部状态。
- 修改公共类成员、接口方法、基类、泛型参数或序列化字段时，必须评估源码兼容与二进制兼容影响。

## 审查清单

- 对象构造后是否始终有效，非法状态能否被类型系统排除？
- 所有权、可空性、生命周期和失败方式是否能从签名读出？
- 是否可以用值语义或组合替代继承与共享所有权？
- 泛型约束和编译错误是否对调用者可理解？
- 公共类型变化是否评估了 API、版本与序列化影响？
