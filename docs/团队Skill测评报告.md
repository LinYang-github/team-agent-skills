# 团队 Skill 测评报告

测评日期：2026-09-10

## 一、总体结论

本轮对仓库现有 10 个 Skill 执行了全量单轮 `skill-up` 基线对照测评。共加载 22 个用例，分别运行启用 Skill 与禁用 Skill 两组，形成 44 次有效模型执行。

- 启用 Skill 的原始规则断言命中率为 **90.0%（126/140）**，无 Skill 基线为 **82.9%（116/140）**，提升 **7.1 个百分点**。
- 启用 Skill 的严格整题通过率为 **13/22（59.1%）**，基线为 **11/22（50.0%）**。
- 人工复核启用组 14 个未命中断言后，确认其中 12 个属于同义表达未覆盖、断言过度限定或判分器误判；语义复核后的规则覆盖为 **138/140（98.6%）**，整题通过为 **20/22（90.9%）**。
- 两个确认存在的行为缺口是：`code-review` 未稳定采用 `[P0]`～`[P3]` 标题，以及 `playwright-tester` 在阻塞场景下遗漏破坏性操作边界。
- 测评当时仓库不具备合并或发布条件：`manifest.yaml` 未登记两个已有 Skill，导致仓库级校验失败。该问题已在后续仓库治理中修复，本次报告整理时的当前门禁已恢复。

阶段判断：Skill 正文整体已达到可用内测水平，核心规则覆盖较完整；测评体系仍处于治理阶段，主要瓶颈是清单一致性、基线隔离、断言准确性和场景覆盖不均衡。

## 四、人工语义复核

### 4.1 判分器误判或断言过窄

启用组 14 个原始未命中中，有 12 个并非实际规则遗漏：

- `common-coding-standards` 已输出“存活/就绪检查”“配置、数据、日志、缓存、临时文件分别配置”和配置覆盖顺序，但断言只接受“健康检查/探活”“可配置目录”等固定表达。
- `cpp-coding-standard` 已在线程入口使用 `try/catch` 并注明不得越过线程边界，但异常断言未覆盖该表达顺序。
- `go-coding-standards` 已用容量为 64 的信号量通道限制并发，但断言只匹配“有界/容量/背压/并发上限”等说明文字。
- `python-coding-standard` 已要求每个连接任务保存到 `set[Task]` 并在完成时移除，语义上满足任务引用管理。
- `ui-ux-standards` 已输出任务化工作区、层级控制和“不改字段、接口、权限、业务逻辑与流程”，但正则未覆盖“工作区”“只调整视觉与交互”等等价表达。
- `playwright-tester` 已明确“未发生浏览器真实访问”，但断言只接受“真实观察/浏览器实际/实际可见”。
- Java 的 JDK 8 用例采用 `ArrayList + HashSet` 正确保持首次出现顺序，判分器却强制要求 `LinkedHashSet/LinkedHashMap`。
- Java 代码审查用例报告输出并未包含禁止短语，judge 仍将其判为命中，属于判分器或 `output_contains.not` 处理异常。

以上项目应修正评测断言，不应为迎合关键词而向 Skill 正文重复堆叠同义词。

### 4.2 确认的行为缺口

#### [P1] `code-review` 严重性格式仍不稳定

用例明确要求按严重程度输出，Skill 也要求问题标题使用 `[P0]`～`[P3]`，实际输出仍使用“高危/中危”。这不是表达等价问题，而是没有遵守自身输出契约，会造成跨项目报告无法稳定聚合和筛选。

完成标准：同一用例连续 3 次均使用 `[P0]`～`[P3]`，且每条问题包含位置、触发条件、影响、证据和最小修复方向。

#### [P1] `playwright-tester` 阻塞响应遗漏破坏性操作约束

实际输出正确拒绝伪造页面通过、Spec 和捕获报告，也列出了服务、登录态和动态路由缺失，但没有说明删除、保存、提交等破坏性操作必须获得明确授权并隔离测试数据。

完成标准：在无服务或无凭据的阻塞场景中，只输出阻塞项和所需输入，同时保留破坏性操作授权边界；连续 3 次稳定命中。

## 五、全项目工程发现

### [P1][已关闭] Skill 目录与版本清单不一致，发布门禁曾被阻断

`skills/csharp-coding-standard` 和当时的 `skills/python-coding-stanard` 目录已存在，但未登记到 `manifest.yaml`；`README.md` 也未列出二者。测评当时 `./scripts/validate-skills.sh` 因此直接失败，任何遵守本仓库流程的 Pull Request 都无法通过合并门禁。

其中 Python 目录名为 `python-coding-stanard`，而 `SKILL.md` 声明名称为 `python-coding-standard`。即使补充清单，目录名与 Skill ID 仍会触发一致性失败。

完成标准：统一 Python Skill ID、目录、评测路径和安装目标；登记 C# 与 Python 的版本和依赖；同步 README；仓库结构校验通过。

处理状态：已完成目录更名、清单登记与 README 同步；本次报告整理时复核 `./scripts/validate-skills.sh` 已通过。

### [P2] 评测引擎配置不统一，默认全量运行不可复现

9 个评测配置默认使用 Claude/Haiku，Java 使用 Codex；本机 Claude 凭据返回余额不足，而默认 npm Codex 启动器又缺少对应原生文件。本轮只能通过显式覆盖引擎、模型和临时 PATH 才完成运行。

完成标准：提供仓库级推荐评测配置或统一执行脚本，固定引擎选择、模型覆盖、隔离目录、输出位置和失败诊断；执行者不需要逐个拼接命令。

### [P2] 基线隔离未固化，容易得到虚假的 Skill 增益

`skill-up` 只保证不向基线工作区安装声明的 Skill，并不会自动隔离 Agent 本机已经安装的全局 Skill。若直接运行 README 当前命令，Codex 基线可能继续发现用户目录中的同名 Skill。

完成标准：全量测评入口创建隔离的 Agent home，只注入必要凭据；增加基线产物检查，发现基线输出声称加载目标 Skill 时直接判定本轮无效。

### [P2] 用例覆盖高度失衡，当前总分主要由 Java 决定

Java 有 13 个场景，其余每个 Skill 只有 1 个。总分不能代表各 Skill 的均衡成熟度，而且新增的重要规则尚无回归用例，例如：

- C++ 存量 SDK 的编码、ABI、target 隔离和兼容性档案；
- 代码审查的全项目与部署交付模式；
- 通用规范的 Git、文档、日志和配置治理；
- UI/UX 的导航、弹窗、原生控件替代、焦点和遮罩；
- 前端的路由、页面嵌入、主题、Mock 与原生浏览器控件约束。

完成标准：每个核心 Skill 至少包含正向、反向、冲突、历史缺陷回归和不应触发五类场景，并分别报告 Skill 级结果，不用全仓平均分掩盖短板。

### [P3] Playwright Skill 缺少 Agent 展示元数据

`playwright-tester` 仍未提供 `agents/openai.yaml`。官方快速校验允许缺省，但团队其他 Skill 已采用统一展示元数据，当前状态会造成安装后的名称、简介和默认提示不一致。

## 六、优先整改路线

1. **仓库门禁（已完成）**：已统一 Python Skill 名称，登记 C# 与 Python，更新 README，`validate-skills.sh` 已恢复通过。
2. **修复两个真实行为缺口**：强化 `code-review` 的 `[P0]`～`[P3]` 输出前自检；完善 Playwright 阻塞场景的破坏性操作边界。

4. **固化全量测评入口**：统一引擎/模型覆盖、隔离 Agent home、结果目录、汇总与错误处理。
5. **补齐覆盖矩阵**：优先覆盖 C++ SDK、部署审查、UI 交互组件和前端工程边界，再扩展其他语言场景。
6. **建立稳定性基线**：关键用例至少运行 3 次，报告最小值、最大值和波动；单轮结果只用于初筛。
