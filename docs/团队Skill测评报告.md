# 团队 Skill 测评报告

## 一、结论

本次测评同步优化了 6 个 Skill，并修正了评测用例对 Skill 加载的干扰和部分同义表达误判。`playwright-tester` 正文按既定范围未修改，只校正评测提示。

在 7 个 Skill、每项 3 次、启用/禁用 Skill 对照的 42 次有效执行中：

- 启用 Skill 的平均行为完整度为 **92.7%**，无 Skill 基线为 **72.7%**，提升 **19.9 个百分点**。
- 启用 Skill 的严格整题通过率为 **17/21（81.0%）**，基线为 **1/21（4.8%）**。
- 已优化的 6 个 Skill 平均行为完整度为 **99.1%**；其中 5 个核心场景三轮全部满足断言。
- `code-review` 为 **94.4%**，一次执行未按 `[P0]`～`[P3]` 输出严重性等级。
- 未改正文的 `playwright-tester` 仅为 **54.2%**，仍是下一阶段首要问题。

结论表明，本轮“关键规则前置为短门禁”的方向有效；当前瓶颈已经从规则覆盖转向 Playwright 工作流边界、多场景评测覆盖和执行成本。

## 四、评测方法修正

评测用例最初同时要求“按团队规范作答”和“不要调用工具”。Claude Code 需要通过内置 `Skill` 工具加载规范，模型因此在部分“启用 Skill”执行中主动放弃加载，造成组别污染。

提示已修正为：若评测提供团队 Skill，应先加载；Skill 加载是唯一允许的工具调用，仍禁止工作区读写和其他工具。该修正不是 Skill 内容优化，但它保证“启用 Skill”组真正有机会执行 Skill。

复核输出时还发现以下断言误判：

- “TS”未被原断言识别为 `TypeScript`；
- “语义令牌”未被识别为“设计令牌”；
- “字段、接口、流程零改动”未被识别为不改变业务边界；
- “异常不外泄”“异常穿过线程入口”因词序不同未命中；
- “显式可配的数据目录”未被识别为可配置目录。

本报告基于同一批 42 次完整执行的原始输出，使用修正后的等价表达断言进行本地重判，未重新调用模型。按最终配置追加复跑时受到评测供应端额度限制，未完成的批次作废且未计入结果。

因此，本报告可以用于判断当前核心场景的规则执行情况；分数同时受到 Skill 优化和评测方法修正影响，不单独用于评价正文改动幅度。

## 五、关键发现

### 1. 短门禁比规则分散更有效

通用、C++、Go 和前端 Skill 在把高风险决策压缩为任务入口附近的短门禁后，三轮核心场景均完整覆盖。正文应保留决策和边界，详细知识继续按需放在 `references/`，不需要把所有参考资料搬回入口。

### 2. 代码审查仍有格式波动

三轮中有一轮未加载 Skill，并使用“高/中/低”代替 `[P0]`～`[P3]`。当前已在正文增加输出前自检，但受评测供应端额度限制，尚未完成再次验证。代码问题识别本身稳定，剩余风险主要是报告契约一致性。

### 3. Playwright 工作流仍未达标

Playwright 在服务、登录态和动态路由真实值缺失时，仍会提出先生成 spec 或文档骨架。它能够拒绝伪造“全部通过”，但没有稳定遵守“只有浏览器真实观察结果才能进入正式产物”的边界。该问题需要单独修改 Skill 正文，不能只靠评测提示解决。

### 4. 执行成本明显增加

| 指标 | 启用 Skill | 无 Skill | 变化 |
| --- | ---: | ---: | ---: |
| 平均耗时 | 21.5 秒 | 13.0 秒 | +65.6% |
| 平均输入 Token | 26,599 | 24,021 | +10.7% |
| 平均输出 Token | 1,966 | 1,483 | +32.6% |

成本上升主要来自 Skill 加载、模型内部判断和回答偏长。后续不能只追求覆盖率，还要增加参考资料路由和输出长度评测。

## 六、下一步

1. 专项整改 `playwright-tester`：没有服务、登录条件和动态路由真实值时，只允许输出阻塞项和所需输入，不生成 spec、`test_case` 或其他正式骨架。
2. 为每个 Skill 扩展到至少 5 类用例：两个核心正向场景、一个不应触发场景、一个规则冲突场景、一个历史缺陷回归场景。
3. 为关键 Skill 增加真实临时仓库和脚本判分，降低纯文本关键词对评分的影响。
4. 将核心硬规则、行为完整度、三轮波动、相对基线和执行成本共同作为准入指标，不以单一总分判定质量。
